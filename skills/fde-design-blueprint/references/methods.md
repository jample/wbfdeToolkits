# fde-design-blueprint 方法参考

> 本文件定义 `fde-design-blueprint` 使用的八个方法，来自设计文档 Simple v0.6 第 6 节和第 13 节（C1–C8）。每个方法给出：定义、要填什么、使用步骤、跨境电商完整填写示例、结果汇入蓝图哪个章节。示例业务内容来自跨境电商既有访谈、观察与确认需求，按 Simple v0.6 模板重组为教学表达；系统内容采用 `fde跨境电商/03_场景设计/Hyp-sys.md` 仿真环境，属于补充设计，不代表原项目已完成技术接入。
>
> 蓝图的八个章节：§1 服务目标与触发；§2 人机流程；§3 指令与知识依据；§4 对话与纠错；§5 工具与系统依赖；§6 输入输出结构；§7 异常与边界；§8 验证样例与确认。

## 1. 需求到蓝图的关键映射

**定义**：把需求文档的每一类内容对应到蓝图要导出的设计项，保证蓝图从需求长出来，而不是重新发明。是 C1 的读需求方法和全程的对照表。

**要填什么**：需求内容 → 蓝图导出什么 → 本项目的具体结论。

**使用步骤**：

1. 读需求 §1–§7，按左列七类内容逐类提取。
2. 为每类写出蓝图应导出的设计项，不确定处标待补。
3. 用它检查：蓝图中任何没有需求来源的设计，必须标注为“本轮 FDE 设计选择”或推演，不得伪装成需求事实。

**跨境电商填写示例**（询盘识别与分派）：

| 需求内容 | 蓝图导出什么 | 询盘实例 |
|---|---|---|
| 角色与目标 | 智能体服务谁、何时发起、帮助完成什么 | 帮销售处理消息，运营协助分类，经理处理归属例外 |
| 当前主流程 | 用户动作、AI 辅助、系统动作和最终结果 | AI 提取摘要和候选，销售核对，系统保存决定 |
| 规则和判断权 | 人工确认点与能力边界 | AI 不自动合并或决定最终 Owner |
| 输入输出 | 内容、字段、是否保存、去向 | 消息 → 摘要 → 查重候选 → 接收记录/首次行动 |
| 异常 | 何时补问、停止建议或转人工 | 来源不可读请求补充；归属冲突交经理 |
| 系统与资料 | 查询、保存和引用的依赖 | ChannelHub 取消息，SalesCRM 查客户并保存询盘 |
| 验收方向 | 智能体走查样例和预期表现 | 疑似重复消息显示理由并等待销售决定 |

**汇入蓝图章节**：全图对照；主要落在 §1（角色与目标）、§2（主流程）、§3（规则）、§6（输入输出）、§7（异常）、§5（系统）、§8.1（验收方向）。

## 2. 人机流程设计

**定义**：把需求主流程改写成“用户动作 / AI 辅助 / 系统动作 / 人工确认 / 输出”的逐步设计。核心模式是 **AI 提议 → 人工确认 → 系统记录**，每步必须标出降级动作（AI 能力不足、系统不可用或权限缺失时怎么办）。对应 C2。

**要填什么**：步骤、触发/输入、AI 处理、输出、人工确认点、异常/降级。

**使用步骤**：

1. 沿需求 §3 正常主流程逐步展开。
2. 每步拆成“AI 提议 → 人工确认 → 系统记录”，把需求中的判断权落成人工确认列。
3. 为每步写降级动作：未授权停止、低置信度只显示原文、无规则只列线索、无 Owner 留异常队列。

**跨境电商填写示例**（询盘蓝图 §2，依据原蓝图第 2–3 节与 Hyp-sys 的 ChannelHub/SalesCRM 说明组合）：

| 步骤 | 触发/输入 | AI 处理 | 输出 | 人工确认 | 异常/降级 |
|---|---|---|---|---|---|
| 1 来源摘要 | 用户选经授权消息 | 提取来源、时间、客户/产品线索、缺失项，保留原文引用 | `InquiryDraft` 摘要 | 用户核对分类和事实 | 未授权停止；低置信度只显示原文 |
| 2 查重建议 | 摘要与允许查询的历史 | 提示候选及匹配理由，不自动合并 | `DuplicateSuggestion[]` | 销售决定关联/新建/独立 | 冲突保留候选并升级经理 |
| 3 优先与 Owner 建议 | 经确认事实和缺失项 | 按已确认规则给建议和理由 | 优先级、候选 Owner、依据 | 销售确认；经理确认例外 | 无规则只列线索 |
| 4 接收与首次行动 | 经确认摘要和 Owner | 检查 Owner、日期、必要问题 | 唯一 Owner、接收状态、首次行动 | 销售最终确认 | 无 Owner 留异常队列 |

**汇入蓝图章节**：§2 人机流程；降级动作同时支撑 §7。

## 3. 指令与知识依据设计

**定义**：规定 Agent 根据哪些规则和资料分析、每条结论的依据如何标注、无依据时如何回答、哪些动作禁止自动执行。对应 C3。

**要填什么**：业务术语与状态、引用与更新责任、无依据处理、禁止动作四组条目。

**使用步骤**：

1. 列业务术语与状态，保证**术语与状态分离**：“可能重复 / AI 建议 / 人工已确认”不可混用。
2. 规定每条提取和建议附 `EvidenceRef`（来源引用），并写明真实来源与保留规则的责任人。
3. 写无依据处理：显示原文、缺口和候选，不补造事实、不下确定结论。
4. 列禁止动作：从需求 §5 约束继承，逐条写明由谁人工确认。

**跨境电商填写示例**（询盘蓝图 §3）：

| 条目 | 已确认设计 | 边界 |
|---|---|---|
| 业务规则与术语 | 区分“可能重复/AI 建议/人工已确认”；结束时只有一个销售 Owner | 状态不可混用 |
| 引用与更新责任 | 每项提取和建议显示 `EvidenceRef` | 真实来源与保留规则待 IT 确认 |
| 无依据处理 | 显示原文、缺口和候选，不下确定结论 | 不补造事实 |
| 禁止动作 | 禁止自动删除、合并、转派、拒绝、外发 | 匹配/归属/接收由人工确认 |

**汇入蓝图章节**：§3 指令与知识依据；禁止动作同步到 §7 边界列。

## 4. 对话补问与纠错设计

**定义**：为智能体运行时的信息缺口设计补问，为用户修正设计回写位置，并标出必须用户决定、AI 不得代替的点。对应 C4。注意这是**设计被建智能体的补问行为**，不是本 Skill 向 FDE 的补问（后者见 SKILL.md 第 7 节）。

**要填什么**：缺口/情形、Agent 补问、用户修正后更新到哪个输出对象、是否必须用户决定。

**使用步骤**：

1. 从 §2 每步的输入中找出“必需但可能缺”的字段，每个设一个补问。
2. 为每个补问规定修正后的回写位置（哪个输出对象、哪个字段）。
3. 标出必须用户决定的点（查重关系、Owner、接收），AI 只给候选和理由。

**跨境电商填写示例**（询盘蓝图 §4）：

| 缺口/情形 | Agent 补问 | 用户修正后更新到 | 必须用户决定 |
|---|---|---|---|
| 型号/规格不明 | “这条只提到‘挂盆’，型号要保留描述还是您补充？” | `InquiryDraft` 产品字段 | 否，可留描述 |
| 候选客户命中多条 | “有 2 条相近记录，关联哪条或新建？” | 查重决定 | 是 |
| 无 Owner 或无日期 | “首次行动的负责人和日期是？” | 首次行动 | 是 |

**汇入蓝图章节**：§4 对话与纠错。

## 5. 工具与系统映射

**定义**：把业务步骤对应到权威系统和能力，标明读写方向和权限状态。系统未确认时写成待补，不承诺接入，不虚构系统名称和接口能力。对应 C5。

**要填什么**：业务步骤 → 权威系统 → REST 能力 → 只读/写回 → 权限状态。

**使用步骤**：

1. 取 §2 每个业务步骤，对照系统说明（本案例 Hyp-sys）找权威系统：权威源唯一，不猜。
2. 写出该步骤需要的 REST 能力（业务化表达，如“多字段搜索客户并返回命中理由”）。
3. 标只读/写回：查询可直接读；**写回一律要求人工确认、幂等键、版本号**。
4. 标权限状态：未取得权限的项标“阻塞构建”，并给缺失时降级方式。

**跨境电商填写示例**（询盘蓝图 §5，Hyp-sys 系统内容为本次补充设计）：

| 业务步骤 | 权威系统 | REST 能力 | 只读/写回 | 权限状态 |
|---|---|---|---|---|
| 发现并汇总消息 | ChannelHub | 获取待处理消息和会话 | 只读 | 待 IT 确认，阻塞构建 |
| 多线索查重 | SalesCRM | 多字段搜索客户并返回命中理由 | 只读 | 待 IT 确认，阻塞构建 |
| 接收 Owner 与首次行动 | SalesCRM | 接收询盘并创建首次行动 | 写回（人工确认、幂等键、版本号） | 待 IT 确认，阻塞构建 |

**汇入蓝图章节**：§5 工具与系统依赖。

## 6. 输入输出数据含义映射

**定义**：蓝图层的数据含义映射——每份来源内容经过什么处理、变成什么输出、去哪里、起什么作用。首期**不写运行时 Mapping DSL**。对应 C6。

**要填什么**：来源内容 → 处理方法 → 输出 → 去向和作用。

**使用步骤**：

1. 为每个输入来源写“保留什么、提取什么”：ID 和时间必须保留，用于回原文核对。
2. 为每个输出对象写“来源 → 处理 → 是否保存 → 去向”，区分草稿写回与临时输出。
3. 检查持久化边界：AI 建议不落库，人工决定才经接口写回；客户表达（数量、期望）保留原意，不改成企业承诺。

**跨境电商填写示例**（询盘蓝图 §6，设计文档 6.5 表）：

| 来源内容 | 处理方法 | 输出 | 去向和作用 |
|---|---|---|---|
| 消息 `message_id`、正文、`received_at` | 保留 ID 和时间，提取正文线索 | 来源引用与询盘摘要 | 用户回到原文核对 |
| 公司、联系方式、国家和产品 | 提取后由用户修正，选用已有字段查询 | 查询输入和客户候选 | CRM 查重 |
| 客户表达的数量、期望月份 | 保留原意，不改为企业承诺 | 数量描述、期望时间和缺失项 | 询盘草稿及后续沟通 |
| 候选与命中理由 | 展示给用户并记录选择 | 关联/保持独立的决定 | 接收及后续跟进 |
| 销售确认的 Owner、动作和日期 | 检查齐备性后保存 | 首次行动 | 作为跟进场景输入 |

**汇入蓝图章节**：§6 输入输出结构。

## 7. 异常与边界设计

**定义**：把需求异常落成智能体行为——每类失败都按“**保留输入 → 补充或转人工**”处理，并明确当前不执行的动作。对应 C7。

**要填什么**：情形、Agent 行为、边界（当前不执行什么）。

**使用步骤**：

1. 收集需求 §4 业务异常，再补技术侧情形（系统失败、权限、来源不可读、版本冲突）。
2. 每类写 Agent 行为：保留输入、说明失败原因、请用户补充或转人工；权限/来源不可读时**不读、不复制、不处理**。
3. 写边界列：不补造事实、未定不标已接收、不自动写回、不外发、不静默重试写回。

**跨境电商填写示例**（询盘蓝图 §7）：

| 情形 | Agent 行为 | 边界 |
|---|---|---|
| 低置信度提取 | 只显示原文和缺口，不下结论 | 不补造事实 |
| 归属冲突 | 保留候选并升级经理 | 未定不标已接收 |
| 来源不可读/未授权 | 明确失败原因；不读取、不复制、不处理 | 不按缺失原文编事实 |
| 写回类动作 | 一律需人工确认 | 首期不自动写回、不外发 |

**汇入蓝图章节**：§7 异常与边界。

## 8. 验证样例与需求追溯

**定义**：用样例走查验证蓝图，并回填需求到蓝图的覆盖关系。样例分**正常、异常、权限/边界**三类；追溯逐条标“需求章节 → 蓝图章节”的覆盖或缺口。形成蓝图不等于系统实现，不补造测试、UAT 或签收结果。对应 C8。

**要填什么**：三类走查样例（输入/前提、预期表现）；追溯表（需求条目、蓝图章节、覆盖结论、差异/待补）；确认范围（依据的需求版本、已确认设计、待确认设计、构建准入、本轮更新、未解决冲突）。

**使用步骤**：

1. 把需求 §7 验收样例改写成智能体走查样例和预期表现，写入 §8.1。
2. 逐条把需求章节映射到蓝图章节，标覆盖/缺口，写入 §8.2；系统域未确认标阻塞构建。
3. 在 §8.3 记录设计决定为“本轮 FDE 选择，待设计会议确认”，写明构建准入结论。

**跨境电商填写示例**（询盘蓝图 §8）：

| 类型 | 样例 | 预期表现 |
|---|---|---|
| 正常 | 信息完整的新询盘 | 摘要、缺失项、建议、唯一 Owner、接收状态、首次行动完整 |
| 异常 | 名称不同但疑似同一项目 | 显示匹配理由并保留人工决定，不自动合并 |
| 权限 | 未授权或不可读来源 | 不读取、不复制、不处理，明确失败原因 |

| 追溯/确认 | 结果 |
|---|---|
| 需求 §1–3 → 蓝图 §1–2 | 已覆盖（四步任务闭环） |
| 需求 §6 依赖 → 蓝图 §5/§7 | 有缺口，技术域未确认，阻塞构建 |
| 构建准入 | 不通过；仅允许虚构样例走查 |

**汇入蓝图章节**：§8.1 走查样例、§8.2 需求追溯、§8.3 确认范围与本轮更新。

## 9. 场景间承接映射

**定义**：设计第二个场景蓝图时，把上游蓝图的已确认输出显式登记为下游输入，保证一个岗位的多个场景拼成完整方案。承接重点在下游蓝图的 C6（输入结构）和 C2（流程起点）。对应 13.9。

**要填什么**：输入（含来源场景与对象）、智能体处理、输出及用途、典型补问。

**使用步骤**：

1. 从上游蓝图 §2/§6 找出已确认的最终输出（如唯一 Owner、接收状态、首次行动）。
2. 在下游蓝图中逐行写“输入 → AI 处理 → 输出/持久化 → 承接关系”，注明直接消费上游哪个对象。
3. 区分下游独有输出与承接输出；不要求两个场景复制相同角色内容。

**跨境电商填写示例**（跟进蓝图承接询盘，设计文档 6.6 表）：

| 输入 | 智能体处理 | 输出及用途 | 典型补问 |
|---|---|---|---|
| 已接收询盘、Owner、首次行动和历史 | 汇总已知事实、未决项和本轮目标 | `FollowupBrief`：会前阅读，通常不必单独保存 | 本轮要澄清什么？ |
| 电话笔记或客户邮件 | 分开事实、判断、期望、承诺和待确认项 | `InteractionSummary`：确认后保存沟通记录 | 希望十一月交付，是客户期望还是已批准承诺？ |
| 已确认沟通结果 | 拆分下一步，补齐责任人与日期 | `ActionItem[]`：支持执行和回访 | 谁负责、何时完成、什么结果算完成？ |
| 已确认事实和允许引用资料 | 生成回复草稿 | `ReplyDraft`：交销售审核、人工发送 | 产品或交期未确认时，哪些内容应暂缓？ |

**汇入蓝图章节**：下游蓝图 §2（流程起点复用上游输出）和 §6（承接对象的输入结构与去向）。

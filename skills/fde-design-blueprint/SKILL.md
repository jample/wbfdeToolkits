# fde-design-blueprint：智能体蓝图设计

把 02 阶段选定/已确认的场景需求，以及设计会议、系统说明、规则与知识资料，加工成可讨论、可实现的岗位智能体蓝图。完成标志：业务方读得懂智能体如何帮助用户，开发方知道输入、输出、知识/工具依赖和用户决定点。

## 1. 适用 / 不适用与最低输入

**最低输入（15.3）**：一份选定场景需求，或足以说明**角色、触发、结果、主流程和人工边界**的等价内容。没有系统说明时先完成业务蓝图，把系统相关接入写为待补。

**有则使用、不强求的输入**：设计会议记录、系统/API 说明、知识与规则资料、已有资产说明、验证样例。

**主要输出**：每个被设计场景一份 `<项目目录>/03_场景设计/scenes/<scene-id>/scene-blueprint.md`，八个章节（蓝图 §1–§8）。不强制单独生成字段映射表、工具清单、决策日志——相关内容先放入蓝图对应章节（§5 工具系统、§6 输入输出、§8.3 确认与本轮更新）。

**不适用**：生产 API 实现与编码、调用客户写入接口执行真实业务、代替客户确认；要初始化新项目脚手架（建立 00–07 目录骨架）→ `fde-init`。本 Skill 是帮助 FDE 做设计的工作助手；蓝图中设计的业务 Skill（如“询盘处理 Skill”）是未来供销售使用的东西，与本 Skill 自身不是同一个东西（设计 10.1）。

**输入参考模板（可选，非调用前置条件）**：

- 需求输入：直接复用 `../fde-discovery-capture/templates/scene-requirement.md` 对应的需求文件。
- 设计讨论输入：[templates/design-input.md](templates/design-input.md)，填好实例见 [examples/design-input.md](examples/design-input.md)。
- 系统上下文输入：[templates/system-context-input.md](templates/system-context-input.md)，实例见 [examples/system-context-input.md](examples/system-context-input.md)。
- 知识与规则输入：[templates/knowledge-rules-input.md](templates/knowledge-rules-input.md)，实例见 [examples/knowledge-rules-input.md](examples/knowledge-rules-input.md)。

**输出模板**：[templates/scene-blueprint.md](templates/scene-blueprint.md)（§1 服务目标与触发 … §8 验证样例与确认，含 8.1 走查样例 / 8.2 需求追溯 / 8.3 确认范围与本轮更新）；填好实例见 [examples/scene-blueprint.md](examples/scene-blueprint.md)。Skill 写入有业务内容的结果，不把空模板交给 FDE 填写。

## 2. 等价需求的最低判断（15.3）

无正式 `scene-requirement.md` 时，只要已有内容能说明**主要用户、触发、期望结果和至少一条正常任务路径**，即可开始 C1–C4 并生成标为“**需求待核验**”的业务蓝图——不得把它标为基于已确认需求。人工决定点、关键异常、输入输出或系统依赖缺失时，分别在 C3、C6、C7 标为待补并定向询问，不要求 FDE 先补齐一份完整需求文档。

若连正常任务路径也无法从材料推导，先用 `fde-discovery-capture` 的 B3–B4 形成最小场景需求，再进入蓝图。需要新增场景时，先建立该场景最小需求定义，再展开蓝图，不要求回头补齐 01 的全部文件。

## 3. 内部 RunRequest 归纳

从当前对话和文件位置自动归纳内部 `RunRequest`（`goal`、`project_path`、`focus`、`source_paths`、`direct_input`、`target_state`），执行顺序、输入去重和异常恢复均遵循 [../../shared/execution-contract.md](../../shared/execution-contract.md)。不得要求 FDE 填 JSON 或五行模板；FDE 用一段自然语言同时给出目标、材料、补充和期望结果时照常处理。保存前才需要 `project_path`；`source_paths` 与 `direct_input` 至少一个包含可用于当前目标的业务信息。

## 4. 读取规则

遵循 [../../shared/merge-rules.md](../../shared/merge-rules.md)：

- FDE 给具体文件时只读该文件及其中明确引用的必要文件；给目录时先按本轮目标筛选最相关材料，告知实际读取范围后处理，不把目录里已有最终答案冒充原始证据。
- 已有目标蓝图必须先读后改，保留与本轮证据无冲突的人工内容和结构。
- 文件不可读时定位到具体文件并继续处理其他材料；不把文件名当正文事实，不猜测不可读内容；来源不可读/未授权时不读、不复制、不处理。
- 证据使用边界：客户确认只在纪要覆盖范围内生效；FDE 直接补充未说明“客户已确认”时不得升级为客户确认；本设计文档和跨境电商示例不作为新客户项目的事实来源。

## 5. 执行步骤 C1–C8

处理顺序：读取需求 → 分配人机职责 → 设计步骤输入/处理/输出 → 对应知识与系统 → 补异常和用户纠错 → 用样例走查 → 保存蓝图。材料足够时连续执行，只有涉及业务选择、事实冲突、人工责任或越权风险时才暂停补问。方法定义与填写示例见 [references/methods.md](references/methods.md)。

蓝图 §1–§8 对应：§1 服务目标与触发；§2 人机流程；§3 指令与知识依据；§4 对话与纠错；§5 工具与系统依赖；§6 输入输出结构；§7 异常与边界；§8 验证样例与确认。

### C1｜读取需求，确定服务目标与触发（蓝图 §1）

- 目的与方法：把需求 §1 的场景目标改写成“智能体服务谁、什么情况下发起、帮用户完成什么结果”，并明确第一阶段非目标。
- FDE 可提供：选定的需求文档地址；本轮设计哪个场景。
- Skill 加工：读需求触发与终点 → 写服务对象/触发/完成结果 → 从需求非目标继承边界 → 基线未取得时只写价值方向，不承诺 ROI/SLA。
- 补问示例：“智能体的服务对象是销售，运营和经理是协作角色，对吗？非目标沿用需求的‘不自动合并、不改归属、不外发’，需要增删吗？”
- 完成判据与下一步：服务对象、触发、结果和非目标清楚，与需求一致 → C2。

### C2｜设计人机流程：用户、AI、系统分工（蓝图 §2）

- 目的与方法：把需求 §3 主流程改写成“用户动作 / AI 辅助 / 系统动作 / 人工确认 / 输出”的逐步表格，关键是标出每步的人工确认点。
- FDE 可提供：复用 C1；如有设计会议记录给出地址。
- Skill 加工：逐步拆“AI 提议 → 人工确认 → 系统记录” → 把需求中的判断权落成人工确认点 → 每步标降级动作。
- 补问示例：“查重这一步，AI 只展示候选和命中理由，由销售决定关联/新建/独立，对吗？”
- 完成判据与下一步：业务方读得懂人机分工、开发方看得出确认点 → C3。

### C3｜梳理指令、知识依据与安全边界（蓝图 §3）

- 目的与方法：把需求 §4 规则和 §5 约束落成“Agent 依据什么规则和资料分析、无依据时如何回答、禁止哪些动作”。
- FDE 可提供：复用前两步；补充规则材料或术语说明地址。
- Skill 加工：列业务术语与状态并保证分离（“可能重复 / AI 建议 / 人工已确认”）→ 规定每条提取和建议附 `EvidenceRef` → 写“无依据时显示原文和缺口，不编事实” → 列禁止自动执行的动作。
- 补问示例：“我把‘AI 建议’和‘人工已确认’在状态上分开，任何写回都要人工确认，未确认内容不进入客户可见结果，可以吗？”
- 完成判据与下一步：规则依据、无依据回答方式和禁止动作清楚 → C4。

### C4｜设计对话补问与用户纠错（蓝图 §4）

- 目的与方法：定义“缺输入时问什么、用户修正后更新哪里、何时必须用户决定”，保证智能体在信息不全时可用而不冒进。
- FDE 可提供：复用前步；说明哪些信息常缺、用户希望在哪些点被询问。
- Skill 加工：为每个必需但可能缺的字段设一个补问 → 规定修正后回写到哪个输出对象 → 标出“必须用户决定、AI 不得代替”的点。
- 补问示例：“型号识别不出时，Agent 保留客户原描述并提示‘型号待确认’，而不是猜一个型号，对吗？”
- 完成判据与下一步：常见缺口都有补问和回写位置、关键决定点归人 → C5。

### C5｜映射工具与系统依赖（蓝图 §5）

- 目的与方法：把需求 §6 依赖和系统说明（如仿真环境 Hyp-sys）对应成“读写什么数据、用现成能力还是后续接入”。系统未确认时写成待补，不承诺接入，不虚构系统名称和接口能力。
- FDE 可提供：系统说明地址；无系统资料时说明“暂无 IT 材料”。
- Skill 加工：每个业务步骤对应权威系统和 REST 能力 → 标只读/写回 → 写回一律要求人工确认、幂等键、版本号 → 未取得权限的项标“阻塞构建”。
- 补问示例：“消息以 ChannelHub 为准、客户/询盘以 SalesCRM 为准；查询只读，接收询盘属写回需人工确认。真实权限没拿到，我标为阻塞构建，先做业务蓝图，可以吗？”
- 完成判据与下一步：每步有权威系统、读写方向和权限状态；缺系统材料时业务蓝图继续，系统列全标待补 → C6。

### C6｜定义输入输出结构与数据去向（蓝图 §6）

- 目的与方法：把需求 §3 的输入输出落成“字段含义、来源、临时或持久化、保存位置与下游用途”。这是蓝图层的数据含义映射，首期不写运行时 Mapping DSL。
- FDE 可提供：复用 C2/C5；确认哪些输出要落库、哪些是临时材料。
- Skill 加工：为每个输出对象写“来源 → 处理 → 是否保存 → 去向” → 区分草稿写回与临时输出 → 保留 ID 和时间用于回原文核对。
- 补问示例：“`InquiryDraft` 先以草稿状态写回 SalesCRM；`DuplicateSuggestion` 只展示不保存 AI 建议，用户决定另经接口写回。这个持久化边界对吗？”
- 完成判据与下一步：每个数据对象的含义、持久化边界和去向清楚 → C7。

### C7｜异常与边界处理（蓝图 §7）

- 目的与方法：把需求 §4 异常落成智能体行为——“何时补问、停止建议或转人工，哪些动作当前不执行”。
- FDE 可提供：复用需求异常；补充系统失败、权限、来源不可读等技术侧情形。
- Skill 加工：对每类失败写“保留输入 → 补充或转人工” → 权限/来源不可读时不读不复制不处理 → 明确当前不执行的动作（自动写回、外发）。
- 补问示例：“来源不可读时，Agent 明确报失败原因、不生成结论；未授权来源直接不处理。这两条写进 §7，对吗？”
- 完成判据与下一步：主要失败都有保留/补充/转人工路径，禁止动作清楚 → C8。

### C8｜验证样例、需求追溯与确认（蓝图 §8）

- 目的与方法：写正常/异常/权限三类走查样例和预期表现，回填需求到蓝图的追溯，记录设计决定和未决项。形成蓝图不等于系统实现，不补造测试、UAT 或签收结果。
- FDE 可提供：复用全程；说明哪些是本轮 FDE 设计选择、哪些待设计会议确认。
- Skill 加工：把需求验收样例改写成智能体走查样例（§8.1）→ 逐条把需求章节映射到蓝图章节，标覆盖/缺口（§8.2）→ 设计决定记为“本轮 FDE 选择，待设计会议确认” → 未决系统项标阻塞构建（§8.3）。
- 补问示例：“三类样例已按预期表现写好；系统域未确认标为阻塞构建，本蓝图只允许虚构样例走查，可以吗？”
- 完成判据与下一步：样例、追溯、确认范围完整，构建准入结论明确 → 保存蓝图并按第 10 节回复。

## 6. 场景间承接（13.9）

同一 Skill 用相同 C1–C8 产出第二个场景蓝图，并**显式承接上游输出**：例如询盘蓝图 C8 确认的首次行动，成为跟进蓝图的输入（`FollowupBrief` 直接消费已接收询盘、Owner、首次行动和历史）。承接关系写入下游蓝图的 §2 和 §6，注明来源场景与输出对象。

岗位、场景、智能体能力和运行 Skill 不必一一对应：一个岗位可有询盘与跟进两个场景，设计为两个面向任务的 Skill，共用消息读取和客户查询能力。先按业务结果组织蓝图，再决定组合方式；不要求两个场景复制相同角色内容。

## 7. 补问规则

遵循 [../../shared/questioning-rules.md](../../shared/questioning-rules.md)：先处理已有材料形成可见初稿，再从缺口中最多选 1–3 个高影响问题，按“场景边界 → 责任与人工决定权 → 主流程闭环/关键输出 → 异常/验收/写回边界 → 名称格式”排序；每个问题说明影响哪个章节、暂时不知道时怎样继续；已回答内容不重复问；FDE 回答“未知/以后补”后本轮不换说法追问。

本 Skill 特有的高影响问题示例：

- **服务对象确认**：智能体主要服务谁？运营/经理是协作角色还是也是直接使用者？（影响 §1、§2）
- **AI 是否只建议**：查重、Owner、优先级等结论，AI 是否只给候选和理由、由人最终决定？（影响 §2 人工确认点、§3 禁止动作）
- **持久化边界**：哪些输出落库、哪些只是会话内临时材料？AI 建议是否不落库？（影响 §6）
- **权限未取得时如何处理**：真实系统权限、字段、接口未确认时，是标“阻塞构建、只做业务蓝图”，还是有替代取证方式？（影响 §5、§8.3 构建准入）

## 8. 目标文件创建与更新（15.3）

- **项目根定位**：优先使用 FDE 明确给出的项目目录；未明确时，从目标文件向上查找含 `00_项目总览/项目总览.md` 的目录作为脚手架根；未找到脚手架时提示可用 `fde-init` 建立完整骨架，但不阻塞本 Skill——仍按 `03_场景设计/` 阶段目录约定创建所需目录（每个 Skill 可独立调用）。
- 目标文件不存在：只对**本轮选定场景**创建一份 `scene-blueprint.md`，按 [templates/scene-blueprint.md](templates/scene-blueprint.md) 填充，材料足够时一次连续完成 §1–§8。不因发现候选场景就为所有候选建文件。
- 目标文件已存在：只更新 §1–§8 中受本轮证据影响的内容，**保护无冲突的人工修改和已确认范围**；合并、冲突并列与确认范围保护遵循 [../../shared/merge-rules.md](../../shared/merge-rules.md)。改变已确认范围时，在 §8.3 记录“原范围、变化、当前状态”。
- 每次更新后在 §8.3 写一条简短变更说明（本轮输入、变更章节、尚未解决的冲突），不额外创建变更表，除非项目已有该文件。

## 9. 质量门

通用输出状态（草稿 / 有条件可用 / 已确认范围）与两层质量检查见 [../../shared/quality-gates.md](../../shared/quality-gates.md)。本 Skill 的六条质量门（15.6）：

1. 服务对象、触发、完成结果和非目标与需求一致。
2. 每一步区分用户动作、AI 辅助、系统动作、人工确认和输出。
3. 输入输出说明来源、含义、保存方式和下游用途。
4. 规则/知识依据、无依据处理、异常降级和禁止动作明确。
5. 工具与系统未知时已隔离，不影响业务蓝图，也未虚构接口能力。
6. 正常、关键异常、权限/边界样例均有预期表现；需求到蓝图可追溯。

满足业务项但系统项待补时标为“**有条件可用**”，只允许业务走查和技术调研，**不得声明生产就绪**；只有实际接口、权限和运行条件得到相应 Owner 确认后，才可另行判断是否进入构建。质量门失败时先自动修复结构性缺项，仍缺业务事实时保存草稿并提出最多 1–3 个问题，不循环重写整份文档。

## 10. 最终回复格式

遵循 [../../shared/questioning-rules.md](../../shared/questioning-rules.md) 的每步回应要求，最终回复必须包含：

- 本步目的与已用输入（文件名、章节/原话位置；直接回答记为本轮 FDE 补充）；
- 加工结果：展示填好的段落或表格，而非仅列字段名；
- 文件更新：蓝图实际保存地址和更新章节；
- 输出状态（草稿 / 有条件可用 / 已确认范围）、已完成范围、构建准入结论；
- 具体缺口与待补：问什么、为何需要、将写入哪里；
- 下一步：复用哪些结果，继续什么内容（如“复用本蓝图首次行动，设计跟进场景”）。

不能只说“已完成”。

## 11. AI 约束

- 形成蓝图不等于系统实现；不补造访谈、测试、UAT 或签收结果，不从蓝图推断已实现或客户已签收。
- 系统未确认时写成待补，不承诺接入，不虚构系统名称和接口能力；无系统资料时完成业务蓝图并把系统域列具体待补项。
- 写回类动作一律要求人工确认、幂等键、版本号；首期不设计自动写回和自动外发。
- “AI 建议”与“人工已确认”状态分离；未确认内容不进入客户可见结果，不把建议伪装成决定。
- 来源不可读/未授权时不读、不复制、不处理，不按缺失原文生成事实。
- FDE 要求 AI 自动合并、自动改派、自动外发等与人工边界冲突的要求时，必须明确指出冲突，不得直接写成已确认设计。这里的人工边界不限于"已确认"范围：需求或蓝图中已写明的人工决定点、禁止动作和推演边界（待客户确认）同样受保护。被拒绝或暂未并入的变更要求作为冲突写入蓝图 §8.3"尚未解决的冲突"（并列要求内容、来源、冲突依据、受影响章节），不并入 §1–§7 设计；只有 FDE 提供覆盖该范围的新确认来源时才修改设计。
- 本 Skill 是帮助 FDE 做设计的工作助手；蓝图中设计的业务 Skill 与本 Skill 自身不是同一个东西（设计 10.1）。

# fde-transfer：客户移交 Skill

根据 `fde-deliver` 已整理的客户交付内容（`06_交付与培训/`），生成并维护 **客户移交总览、每场景移交说明和内容维护与支持说明**，帮助 FDE 与客户明确"收到什么、怎样继续使用、谁维护什么、什么问题由谁处理、哪些内容仍未确认"。

## 1. 与 fde-deliver、fde-assets-archive 的区别

| 对比 | `fde-deliver` | `fde-transfer`（本 Skill） | `fde-assets-archive` |
|---|---|---|---|
| 面向对象 | FDE、客户用户、培训参与者 | 客户接收人、业务 Owner、内容维护人 | 悦智专业 FDE、资产 Owner、后续项目 FDE |
| 核心问题 | 应交付和讲解什么 | 客户实际接收什么、以后谁负责 | 哪些内容可跨项目复用、怎样独立成包 |
| 客户差异 | 保留并讲清 | 作为客户接收范围保留 | 必须隔离或参数化 |
| 源代码/Skill | 在清单中说明用途和路径 | 按交付权利与方式列入客户目录 | 在权限允许时复制到独立可复用资产包 |
| 最终状态 | 可供交付 | 完整接收 / 条件接收 / 暂缓 / 未形成 | 禁止复用 / 待脱敏与评审 / 可在确认范围内复用 |

本 Skill 只形成客户专属移交内容，并可为 `fde-assets-archive` 留下分类建议；真正的资产抽取和通用化不在此执行。

## 2. 适用与不适用

适用：

- 根据交付内容总览整理正式客户移交范围；
- 建立 WorkBuddy Skills、专家、Prompt、模板、源代码、配置说明和文档的客户交付目录；
- 说明每个场景怎样继续使用、由谁维护内容、怎样提出修改；
- 明确使用支持、内容维护、能力修改和新场景需求的边界；
- 记录客户接收人、确认范围、附加条件和未完成项；
- 为后续资产化提供"哪些是客户专属、哪些可以评估复用"的输入。

不适用：

- 需要生成场景交付说明和培训材料 → `fde-deliver`；
- 需要把客户项目转成通用资产包 → `fde-assets-archive`；
- 需要变更需求或蓝图 → 返回对应前序 Skill；
- 需要初始化新项目脚手架（建立 00–07 目录骨架）→ 使用 `fde-init`；
- 需要操作外部系统或实施技术变更 → 不属于本 Skill；
- 只说"帮我打包"但没有交付范围、接收对象或权利说明 → 先形成移交草稿和待确认项，不复制全部文件。

## 3. 最低输入与主要输出

| 输入 | 是否最低需要 | 缺失时怎样处理 |
|---|---|---|
| 阶段 4 交付内容（`06_交付与培训/` 中的交付总览、每场景说明、培训指南或等价内容） | 是 | 没有时先使用 `fde-deliver` 整理 |
| 本轮移交场景（一个或多个 Scene ID） | 是 | 多场景且状态不同时请 FDE 选择 |
| 客户接收角色（业务 Owner、用户代表、内容维护人、必要的技术联系人） | 是 | 可按岗位起草，正式接收前需要明确角色 |
| 实际交付文件路径 | 是 | 路径不明时只生成候选目录，不能写已提供 |
| 交付方式与权利（文档交付、源文件交付、许可使用、受控访问及限制） | 是 | 未确认时标待确认，不默认全部源代码归客户 |
| 内容维护与支持约定 | 否 | 根据标准结构起草，不编造时限和承诺 |
| 客户确认记录 | 否 | 有则按实际范围记录；没有时不得升级状态——路径不齐保持"盘点中"，路径已齐但未走查保持"可供交付"，均不写"已提供/已接收" |

主要输出写入客户项目的 `07_支持移交归档/`：

```text
<客户项目>/
└── 07_支持移交归档/
    ├── 客户移交总览.md
    ├── 内容维护与支持说明.md
    └── scenes/
        └── <scene-id>/
            └── 场景移交说明.md
```

| 输出 | 粒度 | 模板 |
|---|---|---|
| `客户移交总览.md` | 项目：移交范围、交付物、版本标识、交付方式、权利、接收角色、条件和总体状态 | [assets/templates/客户移交总览.md](assets/templates/客户移交总览.md) |
| `scenes/<scene-id>/场景移交说明.md` | 场景：业务范围、WorkBuddy 内容、客户适配、使用入口、维护责任和确认 | [assets/templates/场景移交说明.md](assets/templates/场景移交说明.md) |
| `内容维护与支持说明.md` | 项目/共享：各内容域怎样维护，问题和新需求怎样路由 | [assets/templates/内容维护与支持说明.md](assets/templates/内容维护与支持说明.md) |

客户移交目录只包含客户应接收或受控访问的内容索引。FDE 内部复盘、原始访谈、内部 Prompt 试验、客户无权取得的源代码和资产候选不能默认纳入。

**项目根定位**：优先使用 FDE 明确给出的项目目录；未明确时，从目标文件向上查找含 `00_项目总览/项目总览.md` 的目录作为脚手架根；未找到脚手架时提示可用 `fde-init` 建立完整骨架，但不阻塞本 Skill——仍按 `07_支持移交归档/` 阶段目录约定创建所需目录（每个 Skill 可独立调用）。

## 4. 内部 RunRequest 与读取规则

内部 RunRequest（goal / project_path / focus / source_paths / direct_input / target_state）与统一执行顺序见 [../../shared/execution-contract.md](../../shared/execution-contract.md)。本 Skill 还需在内部推断：

- `scene_scope`：本轮涉及的一个或多个 Scene ID；
- `operation_intent`：新建、盘点、补充、确认（本 Skill 常见）或归档检查；
- `output_scope`：客户项目 `07_支持移交归档/`（本 Skill 的写入目标），不写入独立资产目录。

读取范围、证据边界与增量合并规则见 [../../shared/merge-rules.md](../../shared/merge-rules.md)。本 Skill 特别强调：

- 读取顺序：已有 `07_支持移交归档/` 目标文件 → 本轮直接提供的文件路径与确认记录 → 阶段 4 交付总览和场景说明 → FDE 指定的实际 WorkBuddy 文件；不默认遍历项目历史和归档目录；
- 客户确认只按实际确认来源和范围记录，不能扩展到未确认的场景、版本、文件或责任；
- 已确认范围只有在 FDE 明确提供新的确认来源和覆盖范围时才能修改。

## 5. 执行步骤 E1–E5

五步不是五场会议：材料足够时连续执行，只在实质缺口处补问。详细方法、字段含义和完整填写示例见 [references/transfer-methods.md](references/transfer-methods.md)。

### E1｜确定客户移交范围

- **目的**：确定本轮有哪些场景、哪些文件、哪些客户角色进入移交。
- **FDE 可提供**：项目目录、本轮 Scene ID、阶段 4 目录位置、客户接收角色。
- **Skill 加工**：读取阶段 4 总览和场景说明 → 识别本轮场景、交付内容和接收角色 → 判断本轮是新建、盘点、补充还是确认 → 场景没有完整交付说明时先起草移交目录并标"盘点中"，提示回 `fde-deliver` 补齐。
- **写入**：`客户移交总览.md` §1 移交范围与状态（含明确排除项）、§5 场景接收汇总骨架。
- **确认点**：本轮覆盖哪些场景、明确排除哪些场景。
- **完成判据**：项目、场景、客户角色和本轮范围清楚；不要求先取得全部文件路径。

### E2｜建立客户交付物目录与权利边界

- **目的**：把"要交付什么"和"客户有权取得什么"逐项落实，文件存在不等于客户有权取得。
- **FDE 可提供**：实际文件路径、每项内容的交付方式（源文件/文档/许可使用/受控访问）、第三方许可说明。
- **Skill 加工**：逐项读取实际文件 → 按 Skill、专家、Prompt、模板、代码、MCP 说明和文档分类 → 标关联场景、内容版本和交付方式 → 区分源文件交付、文档说明、许可使用或受控访问 → 将未知权利列为阻塞接收的待确认项，不默认纳入源文件交付。
- **写入**：`客户移交总览.md` §2 客户交付物目录、§3 交付权利与使用边界；场景级对应 `场景移交说明.md` §2、§7。
- **确认点**：源代码、内部 Prompt、第三方内容是否在客户可获得范围内。
- **完成判据**：声称移交的每项内容有真实路径、交付方式和权利状态；路径不明的内容保持"盘点中"，不写已提供。

### E3｜生成逐场景移交和内容维护说明

- **目的**：把交付说明转成客户可接收、可维护的场景移交内容；责任必须写成"在什么情况下，由谁做什么"，不能只写角色名称。
- **FDE 可提供**：客户维护范围约定、各角色岗位对应、已有支持入口。
- **Skill 加工**：从场景交付说明生成场景接收范围 → 补充客户适配、维护责任和问题路由 → 责任按触发条件起草（发现内容错误时谁做什么、业务规则变化时谁确认等）→ 从跨场景内容汇总各内容域的维护方式。
- **写入**：每场景 `场景移交说明.md` §1–§8；`内容维护与支持说明.md` 全部章节；总览 §4 角色与责任。
- **确认点**：客户只说"以后自己维护"时，补问由谁维护哪类内容。
- **完成判据**：每类内容有维护角色、允许调整范围和升级路径；问题路由覆盖使用疑问、内容错误、客户适配、Skill 修改和新场景五类。

### E4｜组织内容走查和客户接收

- **目的**：生成简洁的走查顺序，支持 FDE 与客户实际完成接收确认。
- **FDE 可提供**：走查安排、参与角色、走查后形成的接收记录或纪要。
- **Skill 加工**：按"总览范围 → 交付物逐项 → 用户代表讲使用 → Owner 讲业务规则确认 → 内容维护人讲可调整范围 → 记录接收结论"生成走查顺序；只根据 FDE 提供的走查记录更新结果，不能从"文档已生成/材料已发"推断客户已接收。
- **写入**：`客户移交总览.md` §5 场景接收汇总、§7 客户确认；场景说明 §8 接收条件和确认。
- **确认点**：走查结论的确认角色、确认范围和来源。
- **完成判据**：有实际确认来源时才记录已接收；没有走查记录时不写"已接收"——路径不齐保持"盘点中"，路径已齐保持"可供交付/已提供"原状态。

### E5｜形成移交结论和资产化输入

- **目的**：为每个场景形成明确移交结论，并为 `fde-assets-archive` 留下分类建议。
- **FDE 可提供**：走查结论、附加条件、哪些内容可评估复用的初步判断。
- **Skill 加工**：按四档判定结论——完整接收（范围、交付物、权利、责任、维护和支持说明均由对应角色确认）、条件接收（核心已接收，非阻塞条件有影响、Owner、补齐方式和确认范围）、暂缓（内容、权利、接收角色或关键维护责任不清）、未形成（只完成准备，尚未走查）→ 同时记录通用核心/客户覆盖/不可复用的分类建议，只在客户项目中记录建议，不创建通用资产包。四档结论与交付状态的对应关系：未形成 ⇒ 交付状态保持"盘点中/可供交付"；暂缓 ⇒ 保持接收前状态并记录恢复条件；条件接收、完整接收 ⇒ 交付状态"已接收"，并逐条记录条件与确认范围。
- **写入**：`客户移交总览.md` §5 场景接收汇总、§6 附加条件与未完成项、§8 内部归档提示、§9 本轮更新；场景说明 §8、§9。
- **确认点**：条件接收的每条条件必须有影响、Owner 和补齐方式，不使用笼统"后续优化"。
- **完成判据**：每个本轮场景有四种结论之一及来源；排除项、条件和未完成项全部可见。

## 6. 补问规则

通用规则见 [../../shared/questioning-rules.md](../../shared/questioning-rules.md)：每轮先出可见初稿，再按影响排序最多提 1–3 个问题，已能回答的不重复问，FDE 答"未知/以后补"后本轮不换说法追问。本 Skill 特有的高影响问题：

- **实际文件路径**：声称交付的 WorkBuddy 内容真实路径在哪里？（未读取的路径不得写成已存在或已提供）
- **交付权利**：源代码、内部 Prompt、项目证据是否在客户可获得范围内？权利不清时标待确认，不默认纳入。
- **接收角色与维护责任**：客户侧由谁接收、谁维护哪类内容、问题路由给谁？
- **条件与排除项**：哪些场景、文件或权利明确不在本次移交范围？每条条件的 Owner 和补齐方式是什么？

## 7. 质量门

三类内容状态与通用质量检查见 [../../shared/quality-gates.md](../../shared/quality-gates.md)。本 Skill 客户移交门（五条，全部满足才可记录接收结论）：

1. 移交场景、交付物、内容版本和交付方式清楚；
2. 源文件、文档、许可和受控访问的权利边界明确；
3. 客户接收角色、内容维护责任和问题路由明确；
4. 排除项、条件和未完成项未被隐藏；
5. 客户实际确认有来源；没有确认时不写已接收。

## 8. 最终回复格式

遵循 [../../shared/questioning-rules.md](../../shared/questioning-rules.md) 的 v0.7 七项格式，每轮结束必须说明：

1. 创建或更新了哪些文件；
2. 本轮覆盖哪些项目、场景和内容；
3. 文档状态与交付状态（两者不能互相推断）；
4. 已读取的关键来源和未读取/不可读内容；
5. 已完成什么，仍缺什么，缺口会影响什么；
6. 哪些是 FDE 建议，哪些是客户已确认；
7. 下一步使用哪个 Skill、补什么材料或进入谁的评审。

## 9. AI 约束

- 不把内部 Prompt 试验、原始访谈、内部复盘或客户样例默认列入客户交付物；
- 文件存在不表示客户有权取得；权利不清时不默认客户获得源代码，被多个项目复用的通用核心不因本项目移交自动转为客户所有；第三方材料不得隐去许可问题；
- 不根据"材料已发/文档已生成"推断客户已接收；没有实际确认来源时不写已接收；
- 排除项、条件和未完成项不得隐藏，不使用笼统"后续优化"代替具体条件和 Owner；
- 不根据蓝图虚构不存在的 Skill、源代码、Prompt、MCP 说明或文件路径；文件未读取时不根据文件名猜内容；
- 不在客户移交目录中创建通用资产包，不为资产化实际抽取文件；
- 不执行删除、上传、公开发布或外部发送；不操作外部系统。

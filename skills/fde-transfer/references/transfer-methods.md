# fde-transfer 方法详解：内容合同、权利边界、责任设计与移交结论

> 本文件承载 `fde-transfer` 的详细方法：`SKILL.md` 只保留触发边界、E1–E5 流程和规则入口。内容合同来自 `fde_toolkits_designSimplev0.7.md` 第 3.6–3.9 节，完整示例来自第 6.3 节（合成教学示例，不代表任何客户事实）。

## 1. `客户移交总览.md` 内容合同详解

粒度：项目级。汇总移交范围、交付物、版本/内容标识、交付方式、权利、接收角色、条件和总体状态。不复制每个场景的完整业务步骤，只保留导航和状态。

| 章节 | 要填什么 | 字段含义与填写要点 |
|---|---|---|
| §1 移交范围与状态 | 项目、场景、客户对象、本轮范围、文档状态、交付状态、排除项 | 本轮范围只写本次实际移交的 Scene ID；排除项必须显式列出（哪些场景、文件或权利不在本次范围），防止本轮内容被误认为覆盖整个项目。文档状态取草稿/有条件可用/已确认范围；交付状态取盘点中/可供交付/已提供/已接收，两者不能互相推断 |
| §2 客户交付物目录 | Deliverable ID、类型、名称、关联场景、内容版本、来源路径、交付方式、接收角色、状态 | Deliverable ID 建议稳定短标识（如 `DLV-SKILL-VISIT-PREP`）；类型取 Skill/专家/Prompt/Prompt 模板/源代码/MCP 配置说明/知识规则/文档/示例；内容版本用真实版本标识，没有则标待补，不自动生成虚假正式版本；来源路径必须实际读取过；交付方式见第 4 节权利分类；状态用交付状态四值 |
| §3 交付权利与使用边界 | 所有权/许可/文档/受控访问、第三方限制、是否提供源文件、再分发限制 | 每项内容对应一种权利形态；权利不清标待确认，不默认客户获得源代码；第三方材料写明许可限制，不得隐去 |
| §4 角色与责任 | 用户、业务 Owner、内容维护人、FDE/服务方分别在什么情况下做什么 | 触发式写法："在什么情况下，由谁做什么"，见第 5 节 |
| §5 场景接收汇总 | 每个场景已提供、已接收、条件接收或暂缓的范围和链接 | 逐场景一行，链接到 `scenes/<scene-id>/场景移交说明.md`；不能用完整场景的完整性代表其他场景 |
| §6 附加条件与未完成项 | 条件、影响、临时做法、Owner、补齐方式 | 每条条件必须有具体 Owner 和补齐方式，不使用笼统"后续优化" |
| §7 客户确认 | 确认角色、确认范围、来源/方式、日期（有事实时）、限制 | 只记录客户明确确认的范围；确认可来自纪要或 FDE 转述的明确确认；没有实际确认时留空并说明状态 |
| §8 内部归档提示 | 客户项目哪些内容应保留受控索引，哪些需返还/删除或限制访问 | 只写提示和分类建议，不在此生成通用资产 |
| §9 本轮更新 | 新输入、更新章节和未解决冲突 | 支持连续修订和追溯；重复运行不重复插入 |

## 2. `场景移交说明.md` 内容合同详解

粒度：场景级。独立说明该场景的业务范围、WorkBuddy 内容、客户适配、使用入口、维护责任和确认。不把其他场景的结论自动继承过来。

| 章节 | 必须回答的问题 | 填写要点 |
|---|---|---|
| §1 场景与接收范围 | 哪个场景、服务谁、交付什么结果、哪些内容明确不在本次范围？ | 范围从阶段 4 场景交付说明继承；"不在本次范围"显式列出（如源代码、另一场景的共享内容） |
| §2 WorkBuddy 内容清单 | 使用哪些 Skill、专家、Prompt、模板、知识、代码和 MCP 说明；各自的内容版本和路径是什么？ | 逐项列内容 ID/名称、类型、内容版本、源路径、交付方式；共享引用标"共享"并指向实际路径 |
| §3 使用与培训材料 | 客户使用哪份场景交付说明、培训指南和示例？ | 链接阶段 4 对应文档；示例只能是合成或经授权样例 |
| §4 客户适配 | 哪些术语、变量、目录、输出格式和说明是客户专属？ | 只列客户覆盖项；通用核心的描述不在此改写 |
| §5 内容维护责任 | 谁维护业务规则、知识、Prompt 变量、模板、Skill 或代码说明？变化时怎样提出和确认？ | 触发式责任，见第 5 节；与 `内容维护与支持说明.md` 对应内容域保持一致 |
| §6 支持与变更路由 | 使用疑问、内容错误、客户适配、Skill 修改、新场景分别找谁，需提供什么材料？ | 五类路由分别写接收方和所需最小材料；新场景不塞入既有场景，重新从需求探究开始 |
| §7 权利和限制 | 哪些文件提供源内容，哪些只提供说明或使用权，哪些不可复制/再分发？ | 与总览 §3 一致；本场景视角逐项写清 |
| §8 接收条件和确认 | 已提供/已接收内容、条件、待补、确认人和范围 | 接收结论按第 6 节四档记录，附来源 |
| §9 本轮更新 | 新增材料、变更和冲突 | 简短变更说明 |

## 3. `内容维护与支持说明.md` 内容合同详解

粒度：项目/共享。说明各内容域分别怎样维护，问题和新需求怎样路由。主体是内容域表：

| 内容域 | 客户可维护内容 | 建议维护方式 | 需要 FDE/专业支持的情况 |
|---|---|---|---|
| 客户术语和角色称谓 | 术语表、显示名称、说明文字 | 修改客户覆盖内容并记录日期/Owner | 会改变场景责任、业务含义或多个场景时 |
| Prompt 变量 | 客户名称、输出风格、目录、固定格式等已开放变量 | 按模板说明修改，不改核心边界 | 需要改变任务逻辑、事实依据或人工确认点时 |
| Prompt 模板 | 已明确允许调整的段落和变量 | 保留模板版本与变更摘要 | 修改核心 Prompt、出现跨场景影响时 |
| 业务知识/规则 | 经 Owner 确认的客户内容 | 标来源、Owner、适用范围和更新时间 | 权威来源冲突、规则责任不清时 |
| WorkBuddy Skill/专家 | 客户允许的内容配置或说明 | 按交付权利和提供的维护指南 | 修改 Skill 指令、references、scripts 或专家职责时 |
| 源代码 | 仅在合同允许且交付源文件时 | 按源代码说明和版本管理方式维护 | 缺少开发能力、变更影响未知或涉及通用核心时 |
| MCP 配置说明 | 客户可填写的非敏感参数、字段含义和凭证引用位置 | 不在文档存明文凭证，保留客户自己的配置记录 | 需要新的工具、复杂映射或实际连接处理时 |
| 新场景 | 不直接塞入既有场景 | 重新从需求探究开始 | 由项目 FDE 重新评估范围 |

除内容域表外，文档还必须包含：

- **问题提交最小信息**：提交问题时至少提供场景、操作步骤、输入材料、实际输出和期望输出；
- **允许/不允许分享的材料**：哪些材料可随问题提交，哪些（凭证、未授权客户数据等）不得分享；
- **当前支持入口**：实际的联系人或渠道；没有正式服务依据时写为明确待补项，不编造时限和承诺；
- **内容更新后的确认方式**：客户自行修改后怎样记录版本、什么情况下需要 Owner 或 FDE 再确认。

## 4. 客户交付物目录与权利边界的建立方法（E2）

### 4.1 逐项处理顺序

1. 从阶段 4 交付总览 §3 取出本轮场景声称交付的内容清单；
2. 逐项读取 FDE 指定的实际文件或目录；不可读的定位到具体文件并继续，不根据文件名猜内容；
3. 按类型分类：Skill / 专家 / Prompt / Prompt 模板 / 源代码 / MCP 配置说明 / 知识规则 / 文档 / 示例；
4. 为每项标关联场景、内容版本（没有真实版本标待补）、来源路径；
5. 为每项确定交付方式和权利形态（见 4.2）；
6. 权利未知的一律列入待确认，并写明它阻塞哪项接收结论。

### 4.2 四种权利形态

| 权利形态 | 含义 | 典型对象 | 边界写法 |
|---|---|---|---|
| 源文件交付 | 客户取得文件本体，可在约定范围内修改 | 客户专属 Skill、客户 Prompt 模板、合同允许的源代码 | 写明可修改范围和"核心变化需 FDE 评估"的升级路径 |
| 文档交付 | 客户取得说明文档，不含实现本体 | 培训与使用指南、MCP 配置说明、场景交付说明 | 写明文档覆盖范围（如"仅覆盖本场景"）和不含内容（如凭证、真实配置） |
| 许可使用 | 客户可使用能力但不取得源内容 | 通用专家、通用核心 Skill、平台能力 | 写明"不提供源文件""不提供其他项目内容"、再分发限制 |
| 受控访问 | 客户通过受控方式访问，不持有副本 | 平台内服务、受限知识内容 | 写明访问条件、有效期和终止方式（无事实时标待补） |

### 4.3 关键规则

- 文件存在不表示客户有权取得；权利判断需要 FDE 或合同依据，不能从"文件在项目里"推断；
- 被多个项目复用的通用核心不因本项目移交自动转为客户所有，默认按许可使用处理并标待确认；
- 第三方材料必须写明许可限制，不得隐去；
- 内部复盘、原始访谈、内部 Prompt 试验不进入客户交付物目录，即使它们在同一目录中。

## 5. 内容维护责任与问题路由的设计方法（E3/E4）

### 5.1 触发式责任草稿

责任不写成角色名单，写成"在什么情况下，由谁做什么"。从场景交付说明和蓝图的人工确认点反推触发条件，每类角色至少起草：

| 角色 | 触发式责任示例 |
|---|---|
| 最终用户 | 发现生成内容与来源不一致时，保留原始材料和输出，不自行把错误内容作为客户事实使用 |
| 业务 Owner | 业务术语、规则或输出标准变化时，确认变化范围和是否影响其他场景 |
| 内容维护人 | 在允许的客户覆盖范围内更新术语和模板变量，记录内容版本与修改摘要 |
| FDE/专业团队 | 评估核心 Skill、源代码、专家职责或新场景变化，不替客户长期维护日常业务内容 |

客户只说"以后自己维护"时，补问"由谁维护哪类内容"，先按上表生成触发式草稿供客户核对，不等待完整答案。

### 5.2 问题路由五类

每个场景说明 §6 和维护支持说明中，分别写清五类问题的接收方和所需材料：

| 问题类型 | 默认路由 | 提交所需最小信息 |
|---|---|---|
| 使用疑问 | 先查场景交付说明/培训指南，再找用户代表或内容维护人 | 场景、操作步骤、实际输出 |
| 内容错误 | 内容维护人，涉及业务规则时升级业务 Owner | 错误输出、对应来源材料、期望结果 |
| 客户适配调整 | 内容维护人在允许范围内处理 | 变更内容、影响场景、Owner 确认 |
| Skill/代码修改 | FDE/专业团队评估 | 变更目的、影响范围、是否涉及核心边界 |
| 新场景需求 | 重新从需求探究开始，由项目 FDE 评估 | 业务任务、触发、期望结果，不塞入既有场景 |

## 6. 移交结论的记录方式（E5）

### 6.1 四种结论及条件

| 结论 | 条件 | 记录要求 |
|---|---|---|
| 完整接收 | 场景范围、交付物、权利、责任、维护和支持说明均由对应角色确认 | 写确认角色、范围、来源/方式；不得扩展到未确认场景 |
| 条件接收 | 核心内容已接收；非阻塞条件有影响、Owner、补齐方式和确认范围 | 逐条列条件；不写"后续优化"式笼统条件；不写完整接收 |
| 暂缓 | 交付内容、权利、接收角色或关键维护责任不清 | 写明阻塞原因和解除方式 |
| 未形成 | 只完成准备，尚未开展客户走查和确认 | 默认初始状态；不因为文档齐全而升级 |

### 6.2 来源要求

- 只有 FDE 提供的走查记录、确认纪要或明确转述才能支持"已接收/条件接收"；
- "材料已发""文档已生成"不构成接收来源；
- 每条确认记录至少包含：确认角色、确认范围、来源/方式，日期在有事实时填写；
- 确认范围只覆盖记录内的场景、文件和责任，不自动扩展。

### 6.3 资产化输入提示

E5 同时为 `fde-assets-archive` 留下三分类建议：可能的通用核心、客户覆盖、明确不可复用。只在总览 §8 记录建议，不在客户项目中创建通用资产包。

### 7.2 `场景移交说明.md` 关键章节

```markdown
## 5. 内容维护责任

- "客户经理"称谓和五段式标题：由客户内容维护人在客户覆盖范围内更新，记录内容版本与修改摘要。
- 业务规则（如事实来源要求、不自动外发）：变化时由销售运营 Owner 确认范围和是否影响其他场景。
- 核心 Skill 指令、专家职责或新场景：由 FDE 重新评估，客户不自行修改。

## 6. 支持与变更路由

| 问题类型 | 找谁 | 需提供 |
|---|---|---|
| 使用疑问 | 用户代表，参考培训与使用指南 | 场景、操作步骤、实际输出 |
| 简报内容与来源不一致 | 内容维护人，保留原始材料和输出 | 错误输出、来源材料 |
| 术语/模板调整 | 内容维护人（允许范围内） | 变更内容、Owner 确认 |
```

# fde-discovery-capture：需求探究 Skill

把原始访谈和任务材料变成可回放、可确认、可驱动设计的业务需求。标准化由本文件的方法、模板和检查承担；不要求 FDE 先把材料填进表格，也不要求逐张填表。

## 1. 适用与不适用

适用：

- FDE 已完成一场或多场访谈、任务观察，或手里有任务样例、客户表单，需要整理成需求。
- FDE 没有做过 01 预检，直接拿着访谈材料来，需要直接开展 02。
- 已有需求草稿，需要按新纪要、新样例或经理确认做增量修订。

不适用：

- 访谈还没做，要准备访谈问题、联系人地图、资料请求 → 使用 `fde-discovery-prepare`。
- 需求已确认，要设计人机流程、工具依赖和智能体蓝图 → 使用 `fde-design-blueprint`。
- 要初始化新项目脚手架（建立 00–07 目录骨架）→ 使用 `fde-init`。

## 2. 最低输入与主要输出

- **最低输入**：至少一份访谈、任务观察或任务样例；或 FDE 直接提供的一段原始业务说明。只有项目位置而没有任何业务内容时，指出需要的最小业务信息，不扫描整个项目拼答案。
- **可选对照输入**：01 假设（访前准备）、多角色纪要、规则材料、确认纪要、客户表单。01 假设是可选对照，不是前置条件。
- **输入参考模板**（可选，不是调用前置条件）：[templates/interview-input.md](templates/interview-input.md)、[templates/task-observation-input.md](templates/task-observation-input.md)。
- **主要输出**：`<项目>/02_需求探究/角色与场景总览.md`（模板见 [templates/角色与场景总览.md](templates/角色与场景总览.md)）+ 每个被展开场景的 `<项目>/02_需求探究/scenes/<scene-id>/scene-requirement.md`（模板见 [templates/scene-requirement.md](templates/scene-requirement.md)，八章节 §1 场景定义 … §8 来源与确认摘要）。
- **不强制单独生成**：每种分析方法的中间分析表、单独问题清单、单独来源台账；内容合并进主要输出的对应章节。

## 3. 内部 RunRequest 归纳

先从当前对话和文件位置自动归纳内部 `RunRequest`（goal / project_path / focus / source_paths / direct_input / target_state），规则见 [../../shared/execution-contract.md](../../shared/execution-contract.md)。不得要求 FDE 填 JSON 或固定模板；文件地址、直接回答、修改后的文档三种输入方式等价。

## 4. 读取与合并规则

通用读取范围、证据类型与增量合并规则见 [../../shared/merge-rules.md](../../shared/merge-rules.md)。本 Skill 特别强调：

- **没有 01 文件、直接提供访谈时直接开展 02**：从访谈整理角色与场景，无须补做全部准备表，不回头要求 FDE 先跑 `fde-discovery-prepare`。
- **不将目录里已有最终答案冒充原始访谈输入**：FDE 给目录时先按本轮目标筛选最相关材料并告知实际读取范围；目录中的既有 confirmed/正式成果只能作为"已有目标文件"先读后改，不能当作本轮证据来源。
- 本设计文档和跨境电商示例只作方法、模板和结构参考，不作为新客户项目的事实来源。

## 5. 执行步骤 B1–B6

六步不是六场会议：材料齐时连续执行，只在实质缺口处补问。每步的回应遵循"本步目的 / 已用输入 / 加工结果 / 具体缺口 / 文件更新 / 下一步"的结构。方法定义与完整填写示例见 [references/methods.md](references/methods.md)。

### B1｜归类原始材料

- **目的与方法**：用"原始内容归类"把原话和观察拆成五类——业务目标、任务动作、规则/判断权、异常/例外、待确认疑问，保留每条的"来源 ID + 原句位置"。本步不下结论，只备可追溯素材。
- **FDE 可提供**：访谈纪要、转写、任务演示记录、客户表单或样例的地址；有 01 假设可一并给出对照；没有整理稿时直接把原话粘进对话也可以。
- **Skill 加工**：逐句读原话 → 判定五类归属 → 保留来源回指 → 互相矛盾或含糊的表述标为疑问，不急于合并。
- **补问示例**："`SALES-03` 说'运营转给我以后我确认接收'，`OPS-03` 说'谁最终接收要销售确认'。这两句我先都保留为'转交≠接收'的线索，稍后在 B2 核验角色时确认，可以吗？"
- **写入位置**：归类中间结果留在对话，不单独存文件；结论去向在归类表中标注（如"B2 角色职责""B4 步骤 2"）。会话中断需要恢复时，以目标文件的来源列和待补项为准重建归类，不要求 FDE 重新提供材料。
- **完成判据与下一步**：主要原话都已分类、来源可回指、矛盾点已标注；个别读不了的材料单独列出，不阻塞其余归类。进入 B2。

### B2｜核验并修正角色

- **目的与方法**：用"岗位角色卡"与 01 假设对照，核验谁做什么、谁确认、谁接收，重点修正笼统假设（如"运营负责分派"）。
- **FDE 可提供**：复用 B1 归类结果；多角色访谈各自地址，便于交叉核验。
- **Skill 加工**：按目标/任务/输入/输出/判断权/上下游填角色卡 → 用另一角色的原话交叉核验有争议的责任 → 把 01 假设标为支持/修正/否定并写明依据 → 无指标数据时保留待补，不补造 KPI。
- **补问示例**："运营 `OPS-03` 说只转交并标来源，销售 `SALES-03` 说自己确认接收、冲突交经理。是否可以据此把'运营=分类转交、销售=接收、经理=归属例外'写进角色职责？"
- **写入位置**：角色场景总览 §1 角色卡、§3 角色场景交接；01 假设核验结果写入总览 §5 来源与未决项；同时作为每个场景需求 §2 角色职责的依据。
- **完成判据与下一步**：关键角色的职责、判断权和交接可读懂，争议责任已核验或标为未决。单一角色转述的跨角色责任（无冲突但也无交叉核验，如销售转述"经理决定归属"）标"待核验（单一来源）"，不算已核验，也不视为冲突。进入 B3。

### B3｜5W1H 确定场景定义

- **目的与方法**：用"5W1H 场景卡"把任务词（如"处理消息"）收敛成有触发、有业务结果、有起终点的场景。价值只写方向，不编造未取得基线的 ROI/SLA。
- **FDE 可提供**：复用 B1–B2；确认本轮先展开哪个场景（如询盘识别与分派）。
- **Skill 加工**：找可观察触发 → 定义完整业务结果 → 划起点和终点 → 逐格填 Who/Why/When/Where/What/How → 价值写成"减少什么、改善什么"并标注基线未取得。
- **补问示例**："这个场景的终点，是'销售看到消息'还是'唯一销售确认接收并写下首次行动'？终点定义会决定 §3 主流程写到哪一步。"
- **写入位置**：该场景 `scene-requirement.md` §1 场景定义；场景进入总览 §2 场景清单。
- **完成判据与下一步**：场景有触发、起终点、价值方向和角色分工。进入 B4。

### B4｜写用例主流程

- **目的与方法**：用"用例主流程"沿一条正常任务写每步的输入、执行人、动作、判断、输出和去向。只写正常路径，异常留给 B5。
- **FDE 可提供**：复用前几步；任务回放记录地址，用于核验步骤顺序。
- **Skill 加工**：从触发起逐步推进 → 每步写"输入 / 角色动作 / 判断规则 / 输出去向" → 用任务回放核验顺序 → 把"系统只提示、人工决定"的边界写进判断列。
- **补问示例**："查重这一步，销售是综合公司、联系方式、国家、产品和历史一起判断，还是只按公司名？这决定 §3 步骤 2 的输入字段和'不允许单字段自动合并'这条边界。"
- **写入位置**：该场景 `scene-requirement.md` §3 当前主流程。
- **完成判据与下一步**：读者能回放一条正常任务，知道每步谁做什么、留下什么。进入 B5。

### B5｜异常、规则与验收样例

- **目的与方法**：用"异常及规则表"和"需求到验收对应"，为主流程每步补上触发条件、处理人、动作和返回位置，并把业务结果改写为可用样例核对的表现。
- **FDE 可提供**：复用 B4；经理访谈或规则材料地址；明确"哪些动作绝不允许自动执行"。
- **Skill 加工**：对每步问"这里可能出什么岔" → 写触发条件、处理人、动作、返回位置 → 把禁止自动执行的动作写成明确边界 → 每条业务结果改写为验收样例。
- **补问示例**："归属冲突时，销售先保留还是直接交经理？未确定归属前能否标记'已接收'？这决定步骤 4 的异常和'唯一 Owner'验收项。"
- **写入位置**：异常写入需求 §4 异常流程；约束写入 §5 目标结果与约束；样例写入 §7 验收样例。
- **完成判据与下一步**：主要异常有条件、责任人和返回位置，关键禁止动作和验收样例已列。进入 B6。

### B6｜来源、确认摘要与场景取舍

- **目的与方法**：把每条结论回指来源，记录确认范围，并在场景层说明为何优先某些场景、暂缓另一些。确认可来自已有纪要或 FDE 转述的明确确认，不强制另签文件。
- **FDE 可提供**：复用前几步；确认纪要地址（如有）、系统/基线未取得的说明、场景优先级选择。
- **Skill 加工**：为 §1–§5 关键结论标来源/确认 ID → 系统、基线等未取得项写入 §6 并标"阻塞技术设计/不阻塞业务设计" → 总览 §4 写明取舍理由 → 未决问题集中在 §8 和总览 §5 列出。
- **补问示例**："系统字段和真实频率这轮都没拿到。我把它们写成'阻塞技术设计、不阻塞业务流程设计'的依赖，业务需求照常定稿，可以吗？"
- **写入位置**：需求 §6 信息与依赖、§8 来源与确认摘要；总览 §4 场景取舍、§5 来源与未决项、§6 本轮更新。
- **完成判据与下一步**：§1–§8 完整、来源可追溯、未决项隔离，即构成交给 `fde-design-blueprint`（C1）的 02 输出。"整理好了"不等于客户确认。

## 6. 场景与角色 ID 规则

- 已有 Role/Scene ID 一律沿用，不改写。
- 新 ID 由 Skill 生成：大写连字符格式（SCREAMING-KEBAB-CASE），从业务任务命名，如 `SCN-INQUIRY-TRIAGE`、`SCN-SALES-FOLLOWUP`。
- 场景目录名使用 scene-id 原文（如 `scenes/SCN-INQUIRY-TRIAGE/`），跨 Skill 引用同一 ID 时保持完全一致，不另起小写或别名目录。
- Skill 可以建议新增、拆分、合并或暂缓场景，并说明起终点和业务结果为何重叠或不同；**只有 FDE 明确选择后才创建、合并、改 ID 或删除已有场景文件**。
- 发现候选场景时只为本轮展开的场景建文件，不为所有候选建文件。

## 7. 补问规则

通用规则见 [../../shared/questioning-rules.md](../../shared/questioning-rules.md)：每轮先出可见初稿，再按影响排序最多提 1–3 个问题，已能回答的不重复问，FDE 答"未知/以后补"后本轮不再换说法追问。**每个问题必须同时说明"影响哪个章节"和"暂时不知道时怎样继续"**。本 Skill 特有的高影响问题示例（两段式示范）：

- 转交是否等于接收？（影响角色职责和场景终点；暂时不知道时两种解释并列保留，文档保持草稿，不阻塞其他章节整理）
- 场景终点是"看到消息"还是"唯一 Owner 接收并形成首次行动"？（影响 §3 写到哪一步；暂时不知道时终点按较保守的"看到消息+人工确认"写，差异列入待确认）
- 归属冲突由谁决定、未决前能否标已接收？（影响异常流程和验收；暂时不知道时按"未决前不标已接收"的保守口径继续，决定人列待补）
- 哪些动作绝不允许自动执行？（影响 §5 约束和后续蓝图人工边界；暂时不知道时仅登记候选项，不写成禁止动作）

## 8. 目标文件创建与更新

**项目根定位**：优先使用 FDE 明确给出的项目目录；未明确时，从目标文件向上查找含 `00_项目总览/项目总览.md` 的目录作为脚手架根；未找到脚手架时提示可用 `fde-init` 建立完整骨架，但不阻塞本 Skill——仍按 `02_需求探究/` 阶段目录约定创建所需目录（每个 Skill 可独立调用）。

| 情形 | 处理 |
|---|---|
| 目标文件不存在 | 创建 `角色与场景总览.md`；对本轮展开的每个场景创建一个 `scenes/<scene-id>/scene-requirement.md`，材料足够时一次运行尽量连续完成 §1–§8 |
| 目标文件已存在 | 增量更新本轮证据影响的章节；保留无冲突的人工修改和已确认范围；冲突内容并列写入受影响章节（表格行或章节后引用块）并在 §8 记录；每次更新后在来源/确认摘要中写一条简短变更说明（本轮输入、变更章节、仍未解决的冲突），凡涉及已确认范围的冲突或变更均须记录"原范围、变化、当前状态"。**重复执行同一输入（同一目标文件与同一来源）时复用已有分析，不重复插入场景 ID、表格行、来源、待补问题或更新记录；只有新增证据才追加。** |
| 既有跨境电商式项目 | 沿用 `confirmed/` 下对应文件与既有目录；草稿在工作区形成，明确确认后才更新正式文件；不同时维护内容重复的精简文件和标准文件 |

## 9. 输出状态与质量门

三种输出状态（草稿 / 有条件可用 / 已确认范围）和通用质量检查见 [../../shared/quality-gates.md](../../shared/quality-gates.md)。本 Skill 质量门（需求 §8 写"已确认/待确认范围"）：

1. 场景定义有主体、触发、起点、终点和业务结果。
2. 正常流程的每一步都有输入、角色动作、判断、输出和去向。
3. 至少覆盖对业务结果影响最大的异常，并说明触发、责任人和返回位置。"对业务结果影响最大的异常"至少指会导致结果错误、责任不清、越权执行、信息丢失或流程无法继续的异常；其他低频细节可作为待补项。责任人客观未决（如责任边界本身存在冲突）时，该行标"未决"并列入补问即视为满足本项，但该未决必须反映在输出状态中（文档保持"草稿"，不得标"已确认范围"）。
4. 人工判断权、禁止动作、范围外事项和关键依赖已写清。
5. 正常与关键异常各有一个验收样例；场景边界、角色责任、人工决定、禁止动作和主流程等关键结论能回指来源或明确标为推演。
6. 未决项没有被写成已确认事实。

满足前五项且第六项无违规即可"有条件可用"地进入业务蓝图；系统字段、真实基线和所有长尾异常可以后补。

## 10. 最终回复格式

遵循 [../../shared/questioning-rules.md](../../shared/questioning-rules.md) 的回复约定，每轮结束必须包含：

- **文件位置**：本轮保存或更新的实际路径。
- **输出状态**：草稿 / 有条件可用 / 已确认范围，含确认来源和范围。
- **已完成范围**：本轮完成了哪些章节、依据哪些来源。
- **受影响章节**：本轮变更或冲突涉及的章节清单（增量修订和冲突场景必写）。
- **待补**：未决问题、阻塞项和各自影响（是否阻塞下一阶段）。
- **下一步**：建议补充什么材料、进入哪个 Skill 或哪一步。

## 11. AI 约束

- 原话与 FDE 整理判断分开记录；观察事实与推断分开，推断不写成观察事实。
- 一次样例不推成频率、SLA 或普遍规则。
- 单一角色表述不自动解决跨角色责任冲突；冲突并列保留并补问。
- 没有指标数据不给角色卡补造 KPI。
- 未决项不得写成已确认事实；客户确认只按实际确认来源和范围记录。
- "整理好了"不等于客户确认，也不等于已实现。
- 价值只写方向，不编造未取得基线的 ROI/SLA。

# fde-discovery-prepare 方法说明

本文件定义访前准备 Skill 使用的六个方法，对应设计文档 Simple v0.6 第 4.1/4.3 节和第 11 节 A1–A4。每个方法给出定义、要填字段、使用步骤、一个跨境电商完整填写示例，以及结果汇入 `访前准备.md` 的哪个章节。

示例业务内容取自跨境电商既有实例（来源见 [../examples/README.md](../examples/README.md)），客户为卫浴产品跨境销售企业，通过电话、公共邮箱和渠道消息联系海外客户。示例只作方法演示，不得作为其他客户项目的事实来源。

## 1. 业务背景提取表

**定义**：把公司介绍、售前交接或口头背景中的业务、岗位、项目意图和已知限制分开的一张表。识别的是"需要了解什么"，不是指定 Agent 功能。

**要填字段**：业务背景 / 本轮意图 / 暂不展开 / 待了解，每项附依据或状态。

**使用步骤**：

1. 逐句读输入，把业务事实、岗位线索、意图表述和限制分开；
2. 项目意图（"希望改善销售协同"）与具体功能（"自动分派"）分开记录，后者只能作为待验证问题；
3. 资料没说明的目标、规模、指标写入"待了解"，不从企业类型推断。

**填写示例**（写入访前准备 §1）：

| 字段 | 填写结果 | 依据/状态 |
|---|---|---|
| 业务背景 | 客户经营卫浴产品跨境销售，销售、区域经理和电商运营共同参与客户沟通与协同。 | 来源台账中的模拟简报（SIM-SRC-HANDOFF-001） |
| 本轮意图 | 先理解销售工作周期，重点了解询盘接收和持续跟进。 | 本轮 FDE 补充 |
| 暂不展开 | 报价、库存和订单作为上下游线索，不直接扩展为首批交付范围。 | 本轮范围选择，后续可调整 |
| 待了解 | 团队规模、具体业务入口、当前耗时和业务目标尚需访谈补充。 | 不能从企业类型推断 |

**汇入章节**：访前准备 §1 背景与目标。

## 2. 岗位角色卡（访前假设版）

**定义**：在访谈前用目标、任务、输入、输出、判断权和上下游描述一个岗位的假设画像，全部内容必须可被访谈支持、修正或否定。与需求探究阶段的角色卡的区别：本卡是假设，使用假设语气，标注置信度和验证方式。

**要填字段**：岗位目标 / 主要任务 / 输入 / 输出 / 判断权（假设边界）/ 上下游 / 来源 / 置信度 / 须向本人核验的内容。

**使用步骤**：

1. 从岗位名和业务背景推导目标与任务；
2. 按"他能确认什么、不能确认什么"写判断权边界（如销售只能确认本人任务，不能批准价格政策）；
3. 区分执行者、业务规则解释者、专业/系统信息提供者；
4. 没有指标数据时保留待补，不补造 KPI；未知人名保留岗位名。

**填写示例**（销售代表，写入访前准备 §2）：

| 字段 | 填写结果 |
|---|---|
| 岗位目标（假设） | 及时响应海外客户并持续推进有效机会，在授权边界内形成准确回复和跟进安排 |
| 主要任务（假设） | 查看工作入口、查重接收、准备沟通、整理本轮记录、跟进内部待办 |
| 输入（假设） | 渠道转来的消息、客户历史、上次沟通记录和未完成行动 |
| 输出（假设） | 接收状态、询盘摘要、沟通记录、带责任人与日期的行动 |
| 判断权（假设） | 可能判断重复关系和是否接收；归属争议、价格例外需转交相应角色，不据岗位名推定其有最终价格批准权 |
| 上下游（假设） | 运营提供分类和来源；经理处理归属例外 |
| 来源/置信度 | SIM-SRC-HANDOFF-001 / 中 |
| 须核验内容 | 从消息出现到确认接收的实际步骤和判断依据 |

**汇入章节**：访前准备 §2 联系人与角色假设；每行同时给出"找他具体了解什么"。

## 3. 典型工作日分析

**定义**：按岗位目标推演一个典型工作周期，列出时段/触发、输入、动作、判断和输出，用于从角色任务中识别候选场景。不是某一个场景的流程，而是可能连续、并行或跨日延续的工作。

**要填字段**：与 [../templates/访前准备.md](../templates/访前准备.md) §3 表格一致——时段/触发 / 角色 / 可能的输入 / 可能的动作与判断 / 可能的输出 / 需核验。频率、可能痛点、对应场景线索等额外观察可选地留在对话中或并入"需核验"列，不扩展模板列。

**使用步骤**：

1. 从工作触发（上班开始、新消息到达、异常出现）出发，串出动作与交接；
2. 每个行为写成可观察或可提问的验证点；
3. 顺序、频率、工具未知时标注"待观察"，不编造耗时。

**填写示例**（写入访前准备 §3）：

| 时段/触发 | 角色 | 可能的输入 | 可能的动作与判断 | 可能的输出 | 需核验 |
|---|---|---|---|---|---|
| 工作日开始或新消息到达 | 销售 | 公共邮箱、运营转交、未完成行动 | 查看入口、查找历史、判断是否重复和是否接收 | 接收状态、首次行动 | 实际入口和查重顺序 |
| 渠道消息出现 | 运营 | 渠道消息和来源 | 判断类别、保留来源并转交 | 销售队列待处理项 | 是否决定最终 Owner |
| 归属争议出现 | 区域经理 | 询盘摘要、候选销售和理由 | 核验区域/历史并决定归属 | 唯一销售 Owner | 正式规则和记录位置 |

**汇入章节**：访前准备 §3 典型工作日假设。

## 4. 候选场景归纳（简版 5W1H）

**定义**：把"处理消息"这类任务词归纳为一个有主体、触发、起点、终点和完整业务结果的候选场景。访前阶段只做简版 5W1H，不写完整需求。

**要填字段**：场景 ID/名称 / 主体角色与相关角色 / 触发 / 起点→终点 / 假设的完整业务结果 / 价值方向 / 上下游衔接 / 关键未知 / 验证对象。

**使用步骤**：

1. 从典型工作日中找一个可观察触发；
2. 找到该触发可交付的完整业务结果，划出起点和终点；
3. 价值只写方向（减少什么、改善什么），没有基线不声明 ROI/SLA；
4. 优先展开用户关心的 1–3 个候选，其余保留一行简述；已有 Scene ID 沿用，新 ID 由 Skill 生成。

**填写示例**（写入访前准备 §4）：

| 字段 | 询盘识别与分派（SCN-INQUIRY-TRIAGE） |
|---|---|
| 主体与相关角色 | 销售为主体；运营可能先处理渠道消息；经理只处理分派争议 |
| 触发 | 电话留言、邮件或第三方渠道出现一条疑似销售询盘 |
| 起点→终点 | 团队首次发现该消息 → 唯一销售责任人明确接收并形成首次行动 |
| 假设的完整结果 | 询盘完成分类、查重和最小信息补齐，由唯一 Owner 接收；缺失信息和首次行动已记录 |
| 价值方向 | 减少多入口造成的遗漏、重复联系和无人接收；真实频率基线未取得 |
| 上下游 | 接收后进入销售持续跟进；报价审批和库存承诺不并入本场景 |
| 关键未知 | 运营"分派"究竟指转发消息，还是决定最终销售 Owner |
| 验证对象 | 运营、销售、经理（联合回放同一条消息） |

**汇入章节**：访前准备 §4 候选场景与关键假设。

## 5. 假设表

**定义**：每条假设是一项可被访谈支持、修正或否定的命题，附依据来源、置信度、必须验证的原因和取证方式。假设不是结论；验证之前不得写成客户现状。

**要填字段**：假设命题 / 依据来源 / 推导说明 / 置信度 / 必须向客户验证的原因 / 验证对象与方式。假设 ID 可选（需要跨文档引用时再分配）。写入 [../templates/访前准备.md](../templates/访前准备.md) 时注意模板列较简：§4 表只有"关键未知"和"验证对象"列，命题与依据并入相应单元格；置信度写入 §6.2 的状态列或并入 §4 相应单元格，不扩展模板列。

**使用步骤**：

1. 从背景线索出发，用"线索 → 完整命题"的方式写假设（如：背景说"团队通过电话、邮件和渠道联系海外客户"→ 假设"销售每天可能需要检查多个入口并整理待联系客户"）；
2. 责任、规则和输入缺口优先写成命题；
3. 每条命题配一个具体验证动作（问谁、看什么、要什么样例），不允许"需要智能分派"这类无法证伪的空话。

**填写示例**（写入访前准备 §4 关键未知与 §6.2 来源与待补）：

| 假设命题 | 依据 | 置信度 | 必须验证的原因 | 验证对象/方式 |
|---|---|---|---|---|
| 运营可能负责分类转交，销售可能负责查重接收；最终分派责任未知 | 背景中"销售与运营都参与消息处理"（SIM-SRC-HANDOFF-001） | 中 | 单一岗位名无法确定跨角色责任；误判会写错角色职责 | 分别访谈销售与运营，查看同一条消息流转 |
| 接收询盘前可能需要比较公司、联系方式和历史记录，避免重复联系 | 背景中"客户可能从多个渠道咨询" | 中 | 渠道、查重规则未知 | 请求正常及疑似重复样例各一条 |
| 经理可能处理优先级和归属例外 | 岗位角色卡推导 | 低 | 不能据岗位名推定其有最终价格批准权 | 请经理说明何时介入、作何决定 |

**汇入章节**：访前准备 §4（关键未知与验证对象列）和 §6.2（来源与待补，状态标"假设"）。

## 6. "问题 → 所需证据 → 获取方式"映射

**定义**：把高影响假设逐条变成取证动作——问谁什么、观察什么、需要哪个样例、希望留下什么记录。资料不是越多越好，而是足以验证某个具体判断；无法取得真实材料时给出替代方式。

**要填字段**：待验证问题 / 最小资料或样例 / 现场如何获取 / 无法提供时的替代方式 / 要留下的输出。写入 [../templates/访前准备.md](../templates/访前准备.md) 时注意模板分工：§5 资料与样例请求表含"待验证问题 / 最小资料或样例 / 无法提供时的替代方式 / 预期取得的信息"四列；"现场如何获取"不写入 §5，而是推导为 §6.1 访谈计划表的"重点问题/观察任务"列。

**使用步骤**：

1. 从假设表逐条选出高影响假设（影响角色责任、场景边界或范围）；
2. 为每条定义最小资料（如"一条脱敏渠道询盘及转交记录"，而不是完整邮箱导出）；
3. 排定"先问什么、再看什么"的顺序，写入访谈计划；
4. 每项活动写预期记录内容；无材料时给替代方式（口述步骤、虚构数据演示），不停止整个准备过程。

**填写示例**（写入访前准备 §5 和 §6.1）：

| 待验证问题 | FDE 请求什么 | 现场如何获取 | 要留下的输出 |
|---|---|---|---|
| 转交是否等于接收？ | 一条脱敏渠道询盘及转交记录 | 运营解释转交动作，销售回放接收动作，记录两人使用"分派"一词的含义 | 两个角色的原话、各自动作、接收时的记录和待核验差异 |
| 疑似同一客户怎样判断？ | 一条正常与一条疑似重复任务，保留字段结构即可 | 请销售逐步展示比较了哪些信息、在哪里查看、为何作出判断 | 查重输入、判断顺序、例外和结果去向 |
| 首次行动何时算明确？ | 接收后的行动样例或空白字段结构 | 请销售说明执行人、日期和完成结果由谁填写 | 行动所需内容，以及不完整时的处理方式 |

访谈计划行（顺序 / 对象 / 重点问题或观察任务 / 希望留下的结果）按上表推导，例如：

| 顺序 | 对象 | 重点问题/观察任务 | 希望留下的结果 |
|---|---|---|---|
| 1 | 运营 + 销售 | 用同一条消息回放分类、转交、查重和接收 | 角色分工、主流程、输入输出 |
| 2 | 销售 | 演示正常与疑似重复各一条 | 查重规则、人工判断和主要异常 |
| 3 | 区域经理 | 说明归属冲突及无 Owner 处理 | 例外责任和禁止自动动作 |

**汇入章节**：访前准备 §5 资料与样例请求、§6.1 访谈计划。

# fde-discovery-prepare：访前准备

把一段业务背景变成可执行的取证方案：有依据的角色/场景假设、验证问题、资料请求和访谈计划。产出交给 `fde-discovery-capture` 作为可选对照输入；本 Skill 不代替实际客户访谈。

## 1. 适用与不适用

**适用**

- 首次接触客户，只有售前交接、客户简介、岗位说明、流程材料或一段口头背景；
- 已有初步角色/场景假设，需要把它们组织成"问谁什么、观察什么、需要哪个样例"；
- 已有访前准备文件，拿到新背景材料后要增量修订。

**不适用**

- 已有访谈纪要、任务演示记录要整理成需求 → `fde-discovery-capture`；
- 需求已定、要设计人机分工和智能体蓝图 → `fde-design-blueprint`；
- 要初始化新项目脚手架（建立 00–07 目录骨架）→ `fde-init`。

**最低可开始输入**：一段业务背景 + 本轮希望了解的岗位或业务方向。例如："这是一家卫浴跨境销售企业，希望了解销售与运营处理询盘和持续跟进的工作。"

**有则使用、不强求的输入**：客户介绍、组织/联系人名单、售前材料、已有流程、可用样例和访问限制。

**主要输出**：`<项目目录>/01_预检/访前准备.md`（模板见 [templates/访前准备.md](templates/访前准备.md)，§1 背景与目标 … §6 访谈计划/来源与待补/本轮更新）。可选输入参考模板见 [templates/business-background-input.md](templates/business-background-input.md)——只是可接受内容结构，不是调用前置条件。

**不单独强制生成**独立角色表、假设台账、资料表和访谈表；这些内容合并在主要输出的 §2–§6 中。

## 2. 内部 RunRequest

执行前先按 [../../shared/execution-contract.md](../../shared/execution-contract.md) 第 1 节从对话和文件位置自动归纳内部 `RunRequest`（goal / project_path / focus / source_paths / direct_input / target_state），不复制全文、不要求 FDE 填表。本 Skill 的两个落点：

- `goal` = 访前准备；`focus` 通常是本轮岗位或业务方向（如"询盘与跟进"）。
- `source_paths` 与 `direct_input` 至少有一个包含业务内容；只有项目目录而没有业务内容时，指出需要的最小业务信息（客户大致业务 + 本轮想了解的岗位），不扫描整个项目寻找可以拼成答案的既有正式成果。

统一内部执行顺序与异常恢复规则见 [../../shared/execution-contract.md](../../shared/execution-contract.md) 第 2–3 节。

## 3. 读取规则

合并与冲突的完整规则见 [../../shared/merge-rules.md](../../shared/merge-rules.md)；本 Skill 要点：

1. FDE 给具体文件时，只读该文件及其中明确引用的必要文件。
2. FDE 给目录时，先按本轮目标、文件名、目录位置和更新时间筛选最相关材料，在回复中告知实际读取范围后直接处理，不要求逐文件批准；候选过多或无法判断时先问岗位/场景范围，不默认遍历归档、发布物和全部历史版本。
3. 已有目标文件（访前准备.md）必须先读后改，保留与本轮证据无冲突的人工内容和结构。
4. 文件不可读时定位到具体文件并继续处理其他材料，不把文件名当作正文事实。
5. 证据边界：行业资料和 Skill 推演只能生成假设、建议和待验证问题；客户确认纪要只在覆盖范围内形成已确认事实；FDE 直接补充记为"本轮 FDE 补充"，未说明"客户已确认"时不升级。

## 4. 执行步骤 A1–A4

方法定义与填写示例见 [references/methods.md](references/methods.md)。材料足够时应连续执行多步，不得把每步做成必须由用户点击确认的工作流节点；只有涉及业务选择、事实冲突、人工责任或越权风险时才暂停补问。中间分析表留在对话中，结论写入目标文件对应章节。

### A1｜收集背景，确定要了解的业务范围

- **目的与方法**：用业务背景提取表把业务、岗位、项目意图和已知限制分开。识别的是"需要了解什么"，不是直接指定 Agent 功能。
- **FDE 提供**：至少一段业务背景（文件或文字）+ 本轮调研意图。
- **Skill 加工**：提取业务与岗位线索 → 区分项目意图和具体功能 → 写出本轮范围 → 把资料未说明的目标列为待了解。
- **补问示例**："本轮是了解整个销售周期，还是优先了解询盘与跟进？答案决定后续候选场景的展开深度，写入 §1 本轮范围。"
- **写入章节**：访前准备 §1（背景与目标）。
- **完成判据与衔接**：业务、重点岗位、本轮意图可读懂即进入 A2；没有团队规模或指标不阻塞。

### A2｜从岗位线索形成联系人地图和工作日假设

- **目的与方法**：用岗位角色卡（访前假设版）和典型工作日分析，解决"向谁取证"和"应了解他做哪些任务"。岗位职责未确认前一律使用假设语气。
- **FDE 提供**：自动复用 A1；如有组织说明或联系人名单给地址；没有名单时说明有哪些岗位能参与即可，不要求立刻提供姓名。
- **Skill 加工**：从岗位名推导目标与任务 → 按工作触发和交接串成工作周期 → 区分执行者、业务规则解释者、专业/系统信息提供者 → 标出须向本人核验的内容。
- **补问示例**："谁实际查看公共邮箱？谁把渠道消息交给销售？如同一人兼任直接说明即可。这决定 §2 角色职责拆分和 §6 访谈对象。"
- **写入章节**：访前准备 §2（联系人与角色假设）、§3（典型工作日假设）。
- **完成判据与衔接**：每个关键任务有一个拟访谈岗位即可，未知人名保留岗位名；A3 复用工作日任务归纳候选场景。

### A3｜把任务归成场景，并形成可验证的假设

- **目的与方法**：用候选场景归纳（简版 5W1H）把"处理消息"这类任务词转成有开始、结束和业务结果的场景；用假设表把责任、规则和输入缺口写成可被访谈支持、修正或否定的命题。不能仅写"需要智能分派"这类空话。
- **FDE 提供**：复用 A1–A2；如有流程或售前说明给地址；否则只需选择优先展开哪些任务。
- **Skill 加工**：从一个工作触发出发 → 找到可交付的业务结果 → 划起点终点 → 为关键未知写可验证命题 → 附来源和取证方式。只详细展开用户关心的 1–3 个候选，其余保留简述。
- **补问示例**："首次访谈先验证'如何分给销售'，还是完整了解'消息进入到销售接收'？这决定 §4 优先场景的终点和验证对象。"
- **写入章节**：访前准备 §4（候选场景与关键假设）。
- **完成判据与衔接**：优先场景有起终点、可验证问题及验证对象即可，不必展开所有候选；A4 把验证问题变成资料请求和访谈安排。

### A4｜把假设变成资料请求和访谈计划

- **目的与方法**：用"问题 → 所需证据 → 获取方式"映射，把每条高影响假设变成"问谁什么、观察什么、需要哪个样例"。资料不是越多越好，而是足以验证某个具体判断。
- **FDE 提供**：复用 A3；补充可参与岗位、可用样例和授权限制（如"可以安排销售和运营，只有脱敏邮件，没有系统权限"）。
- **Skill 加工**：逐条选出高影响假设 → 定义最小资料 → 排出"先问什么、再看什么" → 给每项活动写预期记录内容 → 无材料时给替代方式（如用虚构数据演示同样步骤）。
- **补问示例**："这两类样例能否提供？若不能，是否可由客户用虚构数据演示同样步骤？答案决定 §5 资料请求是否启用替代方式。"
- **写入章节**：访前准备 §5（资料与样例请求）、§6（访谈计划、来源与待补、本轮更新）。
- **完成判据**：访谈计划能说明问谁、看什么、希望留下什么。**访谈计划是取证方案，不是已发生的访谈记录**；FDE 按计划取得纪要与观察记录后交给 `fde-discovery-capture`。

## 5. 补问规则

完整排序和集合维护规则见 [../../shared/questioning-rules.md](../../shared/questioning-rules.md)；本 Skill 要点：每轮先出可见初稿，再最多问 1–3 个高影响问题；每个问题说明影响哪个章节、暂时不知道时怎样继续；已能从材料回答的不重复问；FDE 回答"未知/以后补"后本轮不换说法追问，问题连同受影响章节记入 §6.2 待补。

本 Skill 特有的高影响问题示例：

1. **本轮范围**："了解整个销售周期，还是优先询盘与跟进？"——改变 §1 范围和 §4 展开深度。
2. **访谈对象**："哪些岗位能参与本轮访谈？谁实际接触客户消息？"——改变 §2 角色和 §6 安排。
3. **"分派"究竟指什么**："客户材料中的'分派'是转发消息，还是决定最终销售 Owner？"——改变 §2 角色职责和 §4 场景假设的核心责任线。

## 6. 目标文件创建与更新

- **项目根定位**：优先使用 FDE 明确给出的项目目录；未明确时，从目标文件向上查找含 `00_项目总览/项目总览.md` 的目录作为脚手架根；未找到脚手架时提示可用 `fde-init` 建立完整骨架，但不阻塞本 Skill——仍按 `01_预检/` 阶段目录约定创建所需目录（每个 Skill 可独立调用）。
- **不存在时**：按 [templates/访前准备.md](templates/访前准备.md) 创建 `01_预检/访前准备.md`，在一次运行中尽量连续完成 §1–§6；写不出业务内容的章节保留待补，不交空模板。
- **已存在时**：只更新本轮证据影响的章节，保留其他内容；重复执行同一输入不得重复插入行、来源或问题。
- **已有跨境电商式项目**：判定依据是项目目录中已存在 `01_预检/` 等阶段目录和既有正式文件（而非空目录或仅有原始材料）。此类项目沿用既有目录和文件；草稿在工作区形成，用户明确要求且确认范围明确后才更新对应正式文件，不同时维护内容重复的精简文件和标准文件。
- 每次更新后在 §6.3 写一条简短变更说明（本轮输入、更新章节、尚未解决的冲突），不额外创建变更表。

## 7. 质量门

共用两层检查（结构/语义）见 [../../shared/quality-gates.md](../../shared/quality-gates.md) 和 [../../shared/execution-contract.md](../../shared/execution-contract.md) 第 4 节。本 Skill 的四条质量门：

1. 至少有业务背景、本轮范围和重点岗位。
2. 至少一个优先场景具有触发、结果、关键假设和验证对象。
3. 每个高影响假设都对应问题、可接受的证据或替代获取方式。
4. 访谈计划能说明问谁、看什么、希望留下什么，不要求客户先填模板。

四条全部通过标为"有条件可用"，可据此开展访谈；联系人姓名、KPI 和全部候选场景未补齐不构成阻塞。门通过但高影响问题（如本轮范围、访谈对象）尚未获答时，仍按门标状态，但须遵守 [../../shared/quality-gates.md](../../shared/quality-gates.md) 第 1 节的"质量门与高影响问题的关系"：未答问题写入 §6.2 待补并在最终回复中显式列出；存在未决冲突或责任未定时保持"草稿"。未全部通过时保持"草稿"，先自动修复结构性缺项，仍缺业务事实时提出最多 1–3 个问题，不循环重写整份文档。

## 8. 最终回复格式

按 [../../shared/questioning-rules.md](../../shared/questioning-rules.md) 的每步回应格式组织，必须包含：

1. **文件位置**：访前准备.md 的实际保存路径；未保存时明确说明。
2. **输出状态**：草稿 / 有条件可用 / 已确认范围（附质量门未通过项）。
3. **已完成范围**：本次覆盖了 §1–§6 的哪些章节、要点是什么。
4. **待补材料**：具体缺口、会影响什么、如何继续。
5. **下一步**：可复用哪些结果（如"按计划访谈后把纪要交给 fde-discovery-capture"）。

## 9. AI 约束

- 岗位职责、场景和规则未确认前一律使用假设语气（"可能负责…，待核验"）。
- 不能仅写"需要智能分派"这类空话；每条假设必须有依据、验证问题和验证对象。
- 行业资料和 Skill 推演只生成假设、建议和待验证问题，不得写成客户现状或已确认需求。
- 访谈计划是取证方案，不是已发生的访谈记录；不从计划推断访谈结果。
- 不补造 KPI、联系人姓名、真实频率和耗时；未知项保留为待补问题。
- 本设计文档和跨境电商示例只作方法参考，不作为新客户项目的事实来源。

# fde-deliver 交付方法与内容合同

> 本文件承载 `fde-deliver` 的详细方法：三份输出文档的内容合同、WorkBuddy 内容类型盘点方法、通用核心与客户适配的区分、角色化培训设计，以及一个完整填写示例。`SKILL.md` 只保留触发边界、D1–D5 流程和规则引用。

## 1. `交付内容总览.md` 内容合同（项目级）

| 章节 | 必须包含 | 字段含义与填写要点 |
|---|---|---|
| §1 项目范围与状态 | 项目、客户、场景范围、本轮目标、文档状态、交付状态 | 场景范围只写本轮覆盖的 Scene ID，并列出明确排除的场景；作用是防止本轮内容被误认为覆盖整个项目 |
| §2 场景交付清单 | Scene ID、业务目标、目标用户、交付说明路径、当前状态 | 项目级快速导航，一行一个场景，不复制场景细节 |
| §3 WorkBuddy 内容清单 | 内容 ID/名称、类型、关联场景、源路径、内容版本、客户适配、是否准备交付 | 只登记实际读取到的内容；没有路径的标"待补路径"，只有说明的标"仅有说明"；不得根据蓝图虚构文件 |
| §4 共享内容与场景专属内容 | 哪些内容被多个场景共用、哪些只服务一个场景 | 共享内容在项目级登记一次，场景分别引用；避免重复交付和错误共享 |
| §5 客户适配与待补 | 客户术语、输入目录、输出格式、角色称谓、提示词变量、配置说明等 | 将通用核心和客户覆盖区分开；每项适配标明"客户可改"还是"需 FDE 评估" |
| §6 培训与说明材料 | 面向哪些角色、使用哪些材料、场景练习和讲解负责人 | 与 `培训与使用指南.md` 对应，不重复课程细节 |
| §7 客户确认与范围变化 | 已确认/待确认内容、确认来源、变化影响 | 不把 FDE 设计选择写成客户确认；确认来源必须是纪要或 FDE 明确转述 |
| §8 本轮更新 | 输入、更新章节、仍未解决冲突 | 支持连续修订和追溯；每次更新追加一条，不覆盖历史 |

## 2. `场景交付说明.md` 内容合同（场景级）

| 章节 | 必须回答的问题 | 填写要点 |
|---|---|---|
| §1 场景定位 | 服务哪个岗位、什么情况下开始、帮助完成什么业务结果、什么不在范围？ | 从业务任务出发，非目标与目标同等明确 |
| §2 交付内容组成 | 该场景包含哪些 Skill、专家、Prompt、模板、代码或 MCP 说明？哪些是共享引用？ | 每项给名称、类型、路径和来源状态；共享内容标注"共享引用"并指向总览 §4 |
| §3 用户任务流程 | 用户提供什么、WorkBuddy 做什么、用户确认什么、每一步留下什么？ | 用表格逐步写"用户输入/动作、WorkBuddy 帮助、用户必须判断、输出"；人工确认点必须显式 |
| §4 输入与准备 | 需要哪些文件、表格、知识、配置说明或访问前提？由谁提供？ | 区分客户准备的业务材料和 FDE 准备的技术内容 |
| §5 输出与检查 | 输出包含什么、用户怎样判断可用、哪些结果必须回看来源或人工修订？ | 写用户可操作的核对方法，不写系统验收指标 |
| §6 提示词和交互示例 | 用户可以怎样发起；需要补充时怎样回答；错误输入怎样纠正？ | 给出可直接采用的发起语、补充语和纠错示例 |
| §7 内容配置与客户适配 | 客户术语、角色、目录、模板变量、输出格式和可修改范围是什么？ | 只写客户覆盖内容；通用核心的描述不在这里改写 |
| §8 异常、边界和替代方式 | 缺资料、内容冲突、无依据、工具说明不完整时怎样继续？哪些动作不属于本场景？ | 每种异常给继续方式；范围外动作显式列出 |
| §9 练习与讲解建议 | 一条典型任务、一个边界任务、观察点和预期学习效果 | 与培训指南 §4/§6 呼应；练习用合成或经授权材料 |
| §10 来源、确认与待补 | 需求/蓝图/源文件来源、客户确认范围、未决问题和影响 | 客户确认只按实际来源和范围记录；未决项写清影响 |
| §11 本轮更新 | 新增材料、变更章节和未解决冲突 | 每次更新追加一条 |

场景说明必须从业务任务出发，不能只列"导入 Skill、配置 Prompt、查看结果"等产品动作。读者应能理解为什么使用、使用到哪里结束、用户需要承担什么判断。

## 3. `培训与使用指南.md` 内容合同（项目/角色级）

| 章节 | 主要内容 | 填写要点 |
|---|---|---|
| §1 培训目标与范围 | 哪些场景、哪些角色、完成培训后能做什么 | 目标写成行为（"能独立完成一条练习并指出人工核对点"），不写功能宣讲 |
| §2 角色学习路径 | 最终用户、业务 Owner、内容维护人分别学习哪些内容 | 每角色列学习顺序和对应材料 |
| §3 WorkBuddy 基础 | 场景入口、选择 Skill/专家、提供材料、继续对话、修改和保存结果 | 只写三类角色都用得到的基础操作 |
| §4 场景课程单元 | 每场景的业务背景、任务演示、用户操作、人工确认、边界和练习 | 一单元一个场景，引用场景交付说明，不复制全文 |
| §5 内容维护基础 | 怎样修改客户术语、提示词变量、模板、知识来源和说明文档；哪些核心内容需要 FDE 支持 | 区分"客户可维护"与"需 FDE 支持"，不写绝对化承诺 |
| §6 练习设计 | 典型任务、边界任务、练习材料、观察点和完成表现 | "完成表现"帮助讲师判断学习效果，不是系统验收；不建立运行结果判定机制 |
| §7 常见问题 | 不知道怎样提问、资料不足、输出不准确、场景不适用、内容版本不一致等 | 按客户真实疑问补充，不只写泛化 FAQ |
| §8 培训组织建议 | 讲师、助教、客户参与者、材料、时长建议和会后动作 | 按 FDE 指定的培训方式给建议，不固定课程时长 |
| §9 确认与待补 | 客户确认的术语、范围、培训对象和未决项 | 培训材料不宣称替代客户确认 |

## 4. WorkBuddy 内容类型盘点方法（D2 使用）

按八类内容分别盘点。总览 §3 每类至少登记的字段，以及场景交付说明中的体现方式：

| 类型 | 交付总览至少登记 | 场景交付说明中怎样体现 |
|---|---|---|
| Skill | 名称、用途、源路径、内容版本、依赖、关联场景 | 在任务哪一步被使用、用户怎样发起、输出什么 |
| 专家/专家团 | 角色定位、擅长内容、调用/选择方式、边界 | 哪类问题由哪个专家处理，何时需要用户判断 |
| Prompt | 用途、输入、输出、适用范围、维护位置 | 用户或 Skill 怎样使用，哪些信息不得编造 |
| Prompt 模板 | 变量、填写说明、示例、默认值和禁止项 | 客户需要修改哪些变量，哪些核心结构不应随意改变 |
| 源代码 | 组件/脚本名称、路径、作用、依赖说明、归属 | 作为交付实现说明，不在场景手册中粘贴全部代码 |
| MCP 配置说明 | 能力名称、业务用途、所需配置、工具/数据含义、凭证引用方式、限制 | 说明场景哪一步依赖该能力及需要客户准备什么，不声称连接可用 |
| 知识/规则内容 | 权威来源、Owner、适用范围、更新方式 | 说明回答依据、无依据时怎样处理 |
| 示例 | 合成或经授权样例、输入、输出、用途 | 用于讲解和练习，不冒充客户实际数据 |

盘点流程：从蓝图提取应有清单 → 逐项对照 FDE 指定的实际路径 → 每项标记"已找到 / 待补路径 / 仅有说明 / 不在本轮" → 判断共享还是场景专属。蓝图与实际的差异必须显式呈现，不用蓝图内容冒充实际内容。

## 5. 通用核心与客户适配的区分方法

- **通用核心**：与客户身份无关的任务逻辑、事实边界、人工确认点和核心 Prompt 结构。这部分描述写在场景说明的通用章节，不因客户差异而改写。
- **客户适配（客户覆盖）**：客户术语、角色称谓、输入目录、输出格式、Prompt 变量和配置说明。只写入总览 §5 和场景说明 §7，每项标明"客户可改"或"需 FDE 评估"。
- 判断顺序：这项内容换一个客户是否仍然成立？成立 → 通用核心；不成立 → 客户适配。有歧义时作为高影响问题补问一次。
- 禁止反向操作：不得把客户特定术语和字段写成通用核心默认值；也不得为了"统一"把客户适配静默合并进核心描述。

## 6. 角色化培训设计方法（D4 使用）

| 角色 | 学习目标 | 场景练习重点 |
|---|---|---|
| 最终用户 | 从业务任务学会发起、补充、修订和判断结果 | 一条典型任务完整走通，能指出人工核对点 |
| 业务 Owner | 理解场景目标、输出标准、边界和变更确认 | 边界任务：判断哪些变化需要 Owner 确认、是否影响其他场景 |
| 内容维护人 | 理解 Skill/Prompt/模板/知识说明的结构、客户适配点和修改边界 | 修改一个允许的客户覆盖项（术语或变量），并记录内容版本与修改摘要 |

规则：每场景至少一条典型练习和一条边界练习；练习使用合成或经授权内容，不生成客户敏感样例；"完成表现"用于讲师判断学习效果，不构成系统验收。

### 7.2 `场景交付说明.md` 示例片段

```markdown
## 3. 用户任务流程

| 步骤 | 用户输入/动作 | WorkBuddy 帮助 | 用户必须判断 | 输出 |
|---|---|---|---|---|
| 1 确定拜访对象 | 选择客户资料，说明拜访目标和时间范围 | 读取允许使用的材料，列出已取得和缺失内容 | 客户和时间范围是否正确 | 本次准备范围 |
| 2 形成简报草稿 | 请求生成拜访简报 | 按客户信息、历史、产品资料和模板组织草稿，保留来源/缺口 | 事实是否能回到来源，未知项是否明确 | 五段式草稿 |
| 3 人工修订 | 修改事实、删除无关内容、补充关注点 | 按用户修订重新组织，不自行增加事实 | 是否包含无依据价格或承诺 | 用户确认版简报 |

## 6. 提示词和交互示例

- 发起："帮我准备对 <客户名> 的拜访简报，重点是 <产品线>，时间范围近六个月。"
- 补充："补充该客户最近的售后记录；没有就明确标缺口，不要猜。"
- 纠错："第三段的交付日期没有来源，请删除或标注待核实。"

## 8. 异常、边界和替代方式

- 客户资料缺失：列出缺口清单，由用户决定是否继续；不补造客户事实。
- 无依据内容：保留缺口标记，提醒用户回看来源。
- 范围外：不自动外发简报，不替销售形成商务承诺。
```

### 7.3 `培训与使用指南.md` 示例片段

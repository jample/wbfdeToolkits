# fde-deliver：交付内容与培训 Skill

根据已确认的场景需求、智能体蓝图和实际形成的 WorkBuddy 内容，生成并维护客户专属的交付内容总览、每场景交付说明和培训使用指南，帮助 FDE 讲清"交付什么、怎样使用、哪些内容需要客户确认、哪些仍需补充"。本 Skill 只组织文本交付内容：不构建或部署能力，不验证真实系统，不替客户确认。

## 1. 适用与不适用

适用：

- 把一个或多个 WorkBuddy 场景整理成客户交付材料。
- 盘点场景对应的 Skill、专家、提示词、模板、源代码和 MCP 配置说明。
- 从蓝图生成用户使用说明、示例任务、人工确认点和注意事项。
- 为最终用户、业务 Owner 和内容维护人员准备培训内容。
- 根据 FDE 或客户反馈更新交付说明和培训材料。
- 检查每个场景的交付内容是否完整、是否能被客户理解。

不适用：

- 只有客户背景，需要准备访谈 → 使用 `fde-discovery-prepare`。
- 已有访谈/观察，需要形成场景需求 → 使用 `fde-discovery-capture`。
- 需要形成人机流程和智能体蓝图 → 使用 `fde-design-blueprint`。
- 需要整理正式客户接收、维护责任和支持边界 → 使用 `fde-transfer`。
- 需要生成跨客户可复用资产包 → 使用 `fde-assets-archive`。
- 需要初始化新项目脚手架（建立 00–07 目录骨架）→ 使用 `fde-init`。
- 需要修改或执行某个外部系统、服务或连接 → 不属于本 Skill。

## 2. 最低输入与主要输出

**最低输入：**

- 场景需求或等价内容（主要用户、触发、业务结果、正常任务路径和边界）。信息不足以说明完整任务时，先回需求探究。
- 场景蓝图或等价设计（人、AI、WorkBuddy 内容、人工确认、输入输出、知识/工具依赖）。缺失时可先生成"业务交付草稿"，缺口列为设计待补。
- 本轮场景范围（一个或多个 Scene ID）。只有一个明确场景时自动采用；多个候选时只问一次。

**可选输入：**

- 已形成的 WorkBuddy 内容路径（Skill、专家、Prompt、模板、代码、MCP 配置说明）。缺失时先生成"应交付内容清单"，交付状态保持盘点中。
- 客户使用对象和培训安排；已有客户材料（品牌模板、术语、规范）；客户反馈或确认。未明确"客户确认"时一律只记为 FDE 补充。

**主要输出**（写入客户项目的 `06_交付与培训/`——阶段目录编号沿用 FDE 五阶段项目目录约定（01–07），交付与培训对应 `06_`；本 Skill 只写本版定义的这三类内容，不补建范围外文件。既有项目沿用 FDE 指定的现有目录，不强制改名：探测时先列出项目根目录下的阶段目录，优先沿用已存在的标准命名或 FDE 指定的等价目录；存在多个候选或无法判断时向 FDE 确认一次，不自行新建并行目录）：

```text
<客户项目>/06_交付与培训/
├── 交付内容总览.md          # 模板：assets/templates/交付内容总览.md
├── 培训与使用指南.md        # 模板：assets/templates/培训与使用指南.md
└── scenes/<scene-id>/
    └── 场景交付说明.md      # 模板：assets/templates/场景交付说明.md
```

模板：[assets/templates/交付内容总览.md](assets/templates/交付内容总览.md)、[assets/templates/场景交付说明.md](assets/templates/场景交付说明.md)、[assets/templates/培训与使用指南.md](assets/templates/培训与使用指南.md)。

本阶段目录（`06_交付与培训/`）只生成这三类 Markdown。可以引用实际 WorkBuddy 文件路径，但不把源文件复制到阶段目录；是否形成客户文件包由 `fde-transfer` 决定。

**项目根定位**：优先使用 FDE 明确给出的项目目录；未明确时，从目标文件向上查找含 `00_项目总览/项目总览.md` 的目录作为脚手架根；未找到脚手架时提示可用 `fde-init` 建立完整骨架，但不阻塞本 Skill——仍按 `06_交付与培训/` 阶段目录约定创建所需目录（每个 Skill 可独立调用）。

## 3. 内部 RunRequest

先从对话和文件位置自动归纳内部 `RunRequest`（goal / project_path / focus / source_paths / direct_input / target_state），并额外推断三个内部字段：`scene_scope`（本轮 Scene ID）、`operation_intent`（新建/盘点/补充/确认/归档/复用检查）、`output_scope`（本 Skill 固定为客户项目的 `06_交付与培训/` 目录）。规则见 [../../shared/execution-contract.md](../../shared/execution-contract.md)。这些是内部执行信息，不得要求 FDE 填 JSON 或表单。

## 4. 读取规则

通用读取与增量合并规则见 [../../shared/merge-rules.md](../../shared/merge-rules.md)。本 Skill 读取顺序固定为：已有 `06_交付与培训/` 目标文件 → 本轮直接提供的源文件/反馈 → 场景蓝图 → 场景需求 → 项目中与本轮场景明确关联的 WorkBuddy 内容。不默认遍历所有项目历史和归档目录；文件不可读时指出具体文件，继续处理其他内容，不根据文件名猜正文。多轮增量演进时，读取范围声明按轮次追加记录（新轮追加在后，或并入"本轮更新"记录），不用"本轮"字样覆盖指代全部历史轮次。

## 5. 执行步骤 D1–D5

五步不是五场会议：材料足够时连续执行，只在实质缺口处补问。详细方法、内容合同和完整填写示例见 [references/delivery-methods.md](references/delivery-methods.md)。

### D1｜确定场景和本轮交付范围

- **目的**：确认本轮整理哪个项目、哪些场景、面向哪些客户对象。
- **FDE 可提供**：项目目录、场景需求/蓝图位置、本轮目标（新建/补充/修订/供客户确认）。
- **Skill 加工**：读取已有阶段 4 文档 → 识别 Scene ID、用户、业务结果和非目标 → 确认本轮操作意图 → 写入总览 §1–§2。
- **交互确认点**：多个候选场景产生不同总览范围和课程单元时，请 FDE 选择一次。
- **完成判据**：项目、场景、目标角色和本轮结果清楚；不要求先取得所有源文件。

### D2｜盘点实际 WorkBuddy 内容并建立场景映射

- **目的**：把"蓝图计划需要什么"和"项目里实际有什么"分开。
- **FDE 可提供**：实际 Skill、专家、Prompt、模板、代码、MCP 说明的文件/目录路径。
- **Skill 加工**：从蓝图提取应有内容 → 逐项读取实际文件 → 标记已找到/待补路径/仅有说明/不在本轮 → 识别共享与场景专属内容 → 写入总览 §3–§5、场景说明 §2/§4/§7。
- **交互确认点**：蓝图内容只有说明没有实际文件时，确认是否登记为"说明已具备、文件未纳入交付"。
- **完成判据**：所有声称要交付的内容都有实际路径或明确待补状态；不能仅根据名称生成"已提供"。

### D3｜生成每场景交付说明

- **目的**：把需求、蓝图和实际内容组织成一个业务闭环说明。
- **FDE 可提供**：复用 D1–D2 结果；客户术语、角色称谓和输出格式差异。
- **Skill 加工**：从需求提取岗位、触发、价值、起终点和边界 → 从蓝图提取人机步骤、输入输出、人工确认和异常 → 链接实际内容清单 → 生成可直接采用的发起语、补充语、纠错示例 → 客户差异写入客户适配章节，不改通用核心描述 → 未知内容保留为具体待补问题。
- **写入**：每场景 `场景交付说明.md` §1–§10。
- **交互确认点**：客户适配与通用核心的划分存在歧义时补问。
- **完成判据**：客户能看懂场景完成什么、用户怎样使用、交付内容怎样协同、哪些判断仍归用户。

### D4｜生成角色化培训与练习

- **目的**：把场景交付说明转换为可讲解、可练习的培训内容。
- **FDE 可提供**：培训对象（最终用户/业务 Owner/内容维护人）、培训方式和可用的合成或授权练习材料。
- **Skill 加工**：为三类角色分别形成学习目标 → 每场景至少一条典型练习和一条边界练习 → 练习只用合成或经授权内容 → 按 FDE 指定的培训方式给组织建议，不固定课程时长。
- **写入**：`培训与使用指南.md`、场景说明 §9。
- **交互确认点**：培训角色或练习材料来源不明时补问一次。
- **完成判据**：三类角色知道要学什么；练习与真实业务任务一致；培训材料不宣称替代客户确认。

### D5｜完成交付内容检查和客户确认摘要

- **目的**：检查文本交付是否完整，记录客户确认的实际范围。
- **FDE 可提供**：客户确认纪要或明确转述（确认范围、来源）。
- **Skill 加工**：按七个维度检查（业务完整/内容完整/使用可懂/客户适配/培训可用/来源可追溯/确认真实）→ 先自动补齐结构性缺项 → 缺事实的内容列为待补 → 根据确认记录更新总览 §7 和场景 §10 → 报告哪些内容可以进入客户移交准备。
- **交互确认点**：客户确认范围是否包括实际文件和维护方式不清时补问。
- **完成判据**：七个维度逐项有结论；确认只按实际来源和范围记录。

## 6. 交互确认点汇总

只在以下信息会改变交付结果时补问（每轮最多 1–3 个）：

1. 本轮包含哪些场景和客户角色；
2. 蓝图中的内容是否已形成实际文件，实际路径是什么；
3. 哪些内容多场景共享，哪些只属于一个场景；
4. 哪些客户术语、变量、目录和输出格式允许调整；
5. 哪些文件准备提供给客户，哪些只作为 FDE 内部来源；
6. 培训面向哪些角色，使用哪些合成或授权材料；
7. 客户确认了什么，确认范围是否包括实际文件和维护方式。

## 7. 补问规则

通用规则见 [../../shared/questioning-rules.md](../../shared/questioning-rules.md)：先出可见初稿再补问，每轮最多 1–3 个高影响问题，已能回答的不重复问，FDE 答"未知/以后补"后本轮不换说法追问。本 Skill 特有的高影响问题：

- **场景范围**：本轮覆盖哪些场景、明确排除哪些？（影响总览 §1–§2 和培训课程单元）
- **实际文件路径**：声称交付的 WorkBuddy 内容真实路径在哪里？未读取的路径不得写成已存在。
- **客户适配项**：哪些术语、变量、目录和输出格式允许调整？（影响通用核心与客户覆盖的划分）
- **客户确认范围**：客户确认是否包括实际文件和维护方式？（影响总览 §7 和场景 §10 的记录边界）

## 8. 质量门

通用质量检查见 [../../shared/quality-gates.md](../../shared/quality-gates.md)。本 Skill 交付内容门六条：

1. 本轮场景、用户、业务结果和非目标明确；
2. 每场景有完整任务流程、输入输出、人工确认和边界；
3. 声称交付的 WorkBuddy 内容有真实路径或明确待补；
4. 客户覆盖与通用核心分开；
5. 三类角色的培训目标和场景练习可执行；
6. 关键结论有来源，客户确认只按实际范围记录。

满足前五条且第六条无违规，输出可标"有条件可用"；路径盘点、长尾 FAQ 和全部练习细节可后补。但若按 [../../shared/quality-gates.md](../../shared/quality-gates.md) 存在未决冲突或责任未定，文档状态仍保持"草稿"——两处规则不一致时从严执行。

## 9. 最终回复格式

遵循 [../../shared/questioning-rules.md](../../shared/questioning-rules.md) 的 v0.7 七项格式，每轮结束必须说明：

1. 创建或更新了哪些文件；
2. 本轮覆盖哪些项目、场景和内容；
3. 文档状态（草稿/有条件可用/已确认范围）和交付状态（盘点中/可供交付/已提供/已接收）；
4. 已读取的关键来源和未读取/不可读内容；
5. 已完成什么、仍缺什么、缺口影响什么；
6. 哪些是 FDE 建议，哪些是客户已确认；
7. 下一步使用哪个 Skill、补什么材料或进入谁的确认。

## 10. AI 约束

- 不根据蓝图虚构不存在的 Skill、专家、Prompt、模板、源代码、MCP 说明或文件路径；文件未读取时不猜正文。
- 不把内部 Prompt 试验、原始访谈或客户样例默认列入客户交付物。
- 在权利不清时不默认客户获得源代码，也不默认内容可跨客户复用。
- 不根据"材料已发"推断客户已接收；生成文档不等于客户确认接收。
- 不把客户特定术语和字段写成通用核心默认值。
- 客户确认范围不能被新访谈或 FDE 推演自动覆盖；只有 FDE 提供新的确认来源和覆盖范围时才能修改。
- 同一输入重复运行不重复插入场景、文件、来源、问题或确认记录。
- 不执行删除、上传、公开发布或外部发送；不操作外部系统。

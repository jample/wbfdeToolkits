# 共用补问规则与回应格式

> 七个 Skill 共用的"少问但不漏"补问规则和每步回应格式，来自 `fde_toolkits_designSimplev0.6.md` 第 2.1、2.2、10.3、15.5 节和 `fde_toolkits_designSimplev0.7.md` 第 1.5、7.1、7.5 节。各 Skill 的 `SKILL.md` 引用本文件，不重复全文。

## 1. 一轮对话的节奏

| 步骤 | Skill 做什么 | 用户看到什么 |
|---|---|---|
| 识别任务 | 判断本轮目标 | 一句话说明本轮目标 |
| 读取资料 | 获取用户给出的文件/目录；已有路径直接使用 | 已读材料及用途，不可读文件单独指出 |
| 生成初稿 | 按相应方法整理已有内容 | 有具体业务内容、来源和待补点的初稿 |
| 定向补问 | 每轮优先问 1–3 个影响角色、范围、流程或输出的问题 | 问什么、为什么需要、将写入哪里 |
| 合并修订 | 接收文字补充、新文件位置或用户修改的文档 | 修改后的段落与关联影响 |
| 保存成果 | 输出文件并说明当前状态 | 文件链接、可用于什么、仍需哪些材料 |

先根据已有资料生成有内容的初稿，再问影响结果的少量问题。补问帮助 FDE 整理认知和准备补访，不能替代实际客户访谈。用户说"先按这个方向写"表示设计选择；说明"客户已确认"时记录其确认范围和来源即可，不要求重复走一套审批。

## 2. 少问但不漏的补问规则

每轮先处理已有材料并形成可见初稿，再从缺口中最多选择 1–3 个问题。问题按以下顺序排序：

1. 会改变场景起点、终点或第一阶段范围的问题。
2. 会改变责任人、人工决定权或禁止动作的问题。
3. 会使主流程无法闭环或关键输出无法定义的问题。
4. 会改变关键异常、验收结果或系统写回边界的问题。
5. 只影响名称、格式、频率和非关键字段的问题。

前四类优先问，第五类通常作为待补项保存。每个问题至少说明"影响哪个章节"和"暂时不知道时怎样继续"；复杂问题再补充为什么问。已经能从材料回答的问题不重复问；FDE 回答"未知"或"以后补"后，本轮不得换一种说法继续追问。

交付、移交与资产化阶段（v0.7）的高影响问题还包括：

- **场景范围**：本轮覆盖哪些场景，哪些场景明确排除？
- **实际文件**：声称交付/归档的 WorkBuddy 内容真实路径在哪里？（未读取的路径不得写成已存在）
- **交付权利**：源代码、内部 Prompt、项目证据是否在客户可获得范围内？权利不清时标待确认，不默认纳入。
- **接收角色**：客户侧由谁接收、谁维护哪类内容、问题路由给谁？
- **复用权利**：该内容是否允许跨客户复用？客户专属值是否需要参数化或合成重制？
- **客户隔离**：输出根目录是否独立于客户项目？（指向客户项目时停止复制并要求独立暂存路径）

Skill 在当前会话或可选的内部状态中维护"已问问题 + 已回答/待后续"集合。补问前按语义检查是否已经问过；无可靠跨会话状态时，从目标文件的待补项和确认摘要恢复，不要求 FDE 重新说明。

## 3. 资料不完整时怎样继续

| 情况 | 处理方式 |
|---|---|
| 只有一句项目背景 | 形成精简访前假设，补问重点岗位和首次会议目标 |
| 没有 01 文件，直接提供访谈 | 从访谈整理角色与场景，直接开展 02，无须补做全部准备表 |
| 有需求，没有系统说明 | 完成人机流程和业务对象，列出系统相关待补内容 |
| 扫描件或音频暂不可读 | 指明文件，请提供文字/可读版本，继续处理其他资料 |
| 不知道某个异常如何处理 | 先写已知触发条件，将处理人和后续动作作为补问 |
| 已有确认纪要 | 按纪要覆盖范围形成确认内容，不重复询问 |
| 用户要求先出草稿 | 保存有用初稿，集中列出未决内容，后续再补 |

"必需输入"指完成该部分结论所需的信息，不代表缺一项就停止整个 Skill。FDE 回答"暂时不知道"时，保存问题及受影响章节，继续处理其他内容。

## 4. 每步回应格式

每步使用以下内容组织回应，可短可长，但不能只说"已完成"：

| 回应内容 | 要求 | 具体示例 |
|---|---|---|
| 本步目的 | 说明本步解决哪个需求问题 | "这一轮先拆清运营转交与销售接收，避免角色职责写错。" |
| 已用输入 | 文件名、章节/原话位置；直接回答记为本轮 FDE 补充 | "运营访谈 OPS-03、销售访谈 SALES-03。" |
| 加工结果 | 展示填好的段落或表格，而非仅列字段名 | "运营保留来源后转交，销售确认接收，归属争议由经理处理。" |
| 具体缺口 | 问什么、为何需要、会写入哪里 | "首次行动由谁执行、何时完成？用于需求终点和行动输出结构。" |
| 文件更新 | 显示实际保存地址和更新章节；未保存要明确 | "已更新 scene-requirement.md 的角色职责、主流程和来源摘要。" |
| 下一步 | 复用哪些结果，继续什么内容 | "复用这三类角色，展开询盘的正常流转步骤。" |

最终回复必须包含：主要输出文件位置、输出状态（草稿/有条件可用/已确认范围）、已完成范围、待补材料、下一步建议。

交付、移交与资产化阶段（v0.7 §7.5）每轮结束还应说明：

1. 创建或更新了哪些文件；
2. 本轮覆盖哪些项目、场景和内容；
3. 文档状态、交付状态或复用状态（三者不能互相推断，见 [quality-gates.md](quality-gates.md) 第 1 节）；
4. 已读取的关键来源和未读取/不可读内容；
5. 已完成什么，仍缺什么，缺口会影响什么；
6. 哪些是 FDE 建议，哪些是客户或资产 Owner 已确认；
7. 下一步使用哪个 Skill、补什么材料或进入谁的评审。

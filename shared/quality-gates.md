# 共用输出状态与阶段质量门

> 七个 Skill 共用的输出状态定义和阶段质量门，来自 `fde_toolkits_designSimplev0.6.md` 第 15.6 节和 `fde_toolkits_designSimplev0.7.md` 第 1.3、7.1、7.4 节。各 Skill 的 `SKILL.md` 引用本文件，并内联本阶段的具体质量门条目。

## 1. 输出状态

### 1.1 文档状态（v0.6，只用三种）

| 状态 | 含义 | 是否可进入下一阶段 |
|---|---|---|
| 草稿 | 已根据当前材料形成内容，仍有影响核心结论的缺口或冲突 | 可继续补充；不能声称已确认 |
| 有条件可用 | 核心业务闭环完整，少量缺口已隔离并说明影响 | 可在条件范围内进入下一阶段 |
| 已确认范围 | 有明确确认来源，只对记录的角色、场景、规则或设计范围有效 | 可按确认范围进入下一阶段 |

### 1.2 三类内容状态（v0.7 新增，不能互相推断）

| 状态维度 | 可用值 | 含义 |
|---|---|---|
| 文档状态 | 草稿 / 有条件可用 / 已确认范围 | 文档内容是否足以用于本轮工作，哪些范围得到明确确认 |
| 交付状态 | 盘点中 / 可供交付 / 已提供 / 已接收 | WorkBuddy 内容处于内部整理、可提供、已给客户还是客户已确认接收 |
| 复用状态 | 禁止复用 / 待脱敏与评审 / 可在确认范围内复用 | 内容是否允许进入资产化流程，以及复用边界 |

三个状态不能互相推断：文档写得完整不代表文件已提供给客户；文件已提供不代表客户确认接收和维护责任；客户接收不代表有权跨客户复用；形成资产包不代表资产已进入正式资产库。

每个主要输出必须在已有章节中写明范围，不新增表单：

- 访前准备 §1 写"本轮范围"；
- 需求 §8 写"已确认/待确认范围"；
- 蓝图 §8 写"依据的需求版本、适用角色/场景、已确认设计和待确认设计"。

"整理好了"与客户确认不同；确认可来自已有纪要或 FDE 转述的明确确认，不强制另签文件。

**质量门与高影响问题的关系**：质量门按字面条目判定；门全部通过但仍有高影响问题未获回答时，状态仍可按门标为"有条件可用"，但必须满足两个条件——未答问题已写入目标文件的待补章节并说明影响，且最终回复中显式列出这些未答问题。不得因为门通过就让一份范围或责任未定的文档看起来无保留地可用；存在未决冲突或责任未定时保持"草稿"。

**"未决冲突"的界定**：指文档内容本身并存两种相互矛盾、且都影响结论的说法（例如新证据与已确认内容冲突），或责任/范围客观未定。仅登记、未并入设计的被拒变更请求（如越权要求已拒绝并入 §1–§7、只在冲突章节登记并等待确认来源）不单独构成降级理由：文档内容本身无冲突时可标"有条件可用"，但必须写成限定形式（如"有条件可用，含未决变更请求，见 §8.3"），并在最终回复中显式列出。

## 2. `fde-discovery-prepare` 质量门

- 至少有业务背景、本轮范围和重点岗位。
- 至少一个优先场景具有触发、结果、关键假设和验证对象。
- 每个高影响假设都对应问题、可接受的证据或替代获取方式。
- 访谈计划能说明问谁、看什么、希望留下什么，不要求客户先填模板。

达到以上条件即可标为"有条件可用"并开展访谈；联系人姓名、KPI 和全部场景未补齐不构成阻塞。

## 3. `fde-discovery-capture` 质量门

- 场景定义有主体、触发、起点、终点和业务结果。
- 正常流程的每一步都有输入、角色动作、判断、输出和去向。
- 至少覆盖对业务结果影响最大的异常，并说明触发、责任人和返回位置。
- 人工判断权、禁止动作、范围外事项和关键依赖已写清。
- 正常与关键异常各有一个验收样例；场景边界、角色责任、人工决定、禁止动作和主流程等关键结论能回指来源或明确标为推演。
- 未决项没有被写成已确认事实。

满足前五项且第六项无违规即可"有条件可用"地进入业务蓝图；系统字段、真实基线和所有长尾异常可以后补。

"对业务结果影响最大的异常"至少指会导致结果错误、责任不清、越权执行、信息丢失或流程无法继续的异常；其他低频细节可以作为待补项。来源可使用文件与章节/原话 ID、任务样例位置、确认纪要及范围，或"本轮 FDE 补充：原文摘要"。

## 4. `fde-design-blueprint` 质量门

- 服务对象、触发、完成结果和非目标与需求一致。
- 每一步区分用户动作、AI 辅助、系统动作、人工确认和输出。
- 输入输出说明来源、含义、保存方式和下游用途。
- 规则/知识依据、无依据处理、异常降级和禁止动作明确。
- 工具与系统未知时已隔离，不影响业务蓝图，也未虚构接口能力。
- 正常、关键异常、权限/边界样例均有预期表现；需求到蓝图可追溯。

满足业务项但系统项待补时标为"有条件可用"，只允许业务走查和技术调研；只有实际接口、权限和运行条件得到相应 Owner 确认后，才可另行判断是否进入构建。

## 5. v0.7 三个质量门

### 5.1 `fde-deliver` 交付内容门

- 本轮场景、用户、业务结果和非目标明确；
- 每场景有完整任务流程、输入输出、人工确认和边界；
- 声称交付的 WorkBuddy 内容有真实路径或明确待补；
- 客户覆盖与通用核心分开；
- 三类角色的培训目标和场景练习可执行；
- 关键结论有来源，客户确认只按实际范围记录。

### 5.2 `fde-transfer` 客户移交门

- 移交场景、交付物、内容版本和交付方式清楚；
- 源文件、文档、许可和受控访问的权利边界明确；
- 客户接收角色、内容维护责任和问题路由明确；
- 排除项、条件和未完成项未被隐藏；
- 客户实际确认有来源；没有确认时不写已接收。

### 5.3 `fde-assets-archive` 资产包门

- 每个场景形成独立业务闭环，项目共享资产有明确引用；
- WorkBuddy Skill、专家、Prompt、模板、代码和 MCP 说明有完整清单；
- 每个资产包文件能回到项目来源和转换动作；
- 客户覆盖、项目证据和受限内容已隔离；
- 权利和第三方依赖有状态；
- 有复用指南、客户覆盖模板和合成示例；
- 未经专业确认不写成正式可发布资产。

## 6. `fde-init` 初始化质量门

- 目录骨架齐全（00–07 阶段目录、00 两份文件、各阶段 README 占位）。
- 项目总览含项目名称与项目概要。
- 空白章节标"待补"而非虚构——未提供的信息不从项目名推测。
- 未覆盖既有内容——已有非空文件原样保留。

四条全部通过为"有条件可用"，可据此开始访前准备；可选信息（客户简称、计划周期、参与角色）未补齐不构成阻塞。

## 7. 避免过强约束

不按文件数量或表格填满率判断完成，而看：

- 01 能否据此开展有效访谈；
- 02 能否还原任务与主要异常，并让客户确认范围和结果；
- 03 能否据此讨论智能体方案并开展后续技术设计。

缺少 API 不妨碍写业务需求；缺少基线不妨碍描述价值方向；任务简单时角色和流程可放在同一表格。进入实际开发后，再按需要补系统合同和详细技术设计。
